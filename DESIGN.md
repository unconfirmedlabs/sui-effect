# @unconfirmed/sui-effect: specification

Status: the 0.6.0 scope. 0.1.0 to 0.5.0 grew a wallet core around the
lifecycle (intents and a semantic screen, account signers, a sealed keystore,
portable storage, Enoki, a script preset, a Promise face for SDK extensions);
0.6.0 removes it and keeps the wrapper. That code moves to the miso wallet's
own codebase. What is not listed here is out of scope (section 15).

## 0. Purpose in one paragraph

@unconfirmed/sui-effect is an Effect v4 program to interact with the Sui blockchain: a light wrapper around the official `@mysten/sui` 2.x TypeScript SDK that makes it safer to use and takes advantage of Effect for reliability, convenience and a better developer experience. The SDK keeps doing BCS, transaction building, signing and transport. This package owns the shape of the program around it: a one-to-one Effect wrap of the SDK's Core API (`SuiCore`), a convenience tier of decoded reads (`Sui`), closed error unions with outcomes on every function, the transaction lifecycle as functions with typed outcomes, crash-safe submission, and time, retry and interruption through Effect so tests can drive them with scripted answers. Every public name mirrors the SDK name it wraps, so an agent that knows the SDK can guess this package.

The rules that follow from that purpose, in every section below:

- **Closed error unions with outcomes.** Every public function states its error union in words and in its type; no `Promise` and no `unknown` in an error channel; every failure is placed on one axis (`applied`, `not_applied`, `unknown`).
- **SDK names.** Where the SDK has the concept, the name and the option names are the SDK's (`fromSecretKey`, `ephemeralSigner`, `listX` → `streamX`).
- **One obvious way** to do each thing: no aliases, no second spelling of the same operation.
- **Objects, never transaction history, are evidence**: reconcile, the alias check and `Tx.attach` read objects; a history listing is a convenience read.
- **No implicit state machines**: the lifecycle is functions over values (`Built`, `Signed`, `Executed`); the only state is the journal, which is explicit and replaceable, and the sender locks, which are reference-counted and scoped to the client.

Application code, scripts, agents and SDKs built on Sui all use the same entry points: `Sui` to read, `Tx` to write, `Signer` values to sign.

## 2. `SuiCore`: the mechanical tier

A hand-written 1:1 Effect wrap of `ClientWithCoreApi` from `@mysten/sui/client`.

- Every key of `SuiClientTypes.TransportMethods` is present, none optional on our side. A type-level test asserts `Exclude<keyof TransportMethods, keyof SuiCore["Service"]>` is `never`.
- `Include` generics are preserved exactly as the SDK declares them.
- Every call forwards the AbortSignal from `Effect.tryPromise((signal) => ...)` into `CoreClientMethodOptions.signal`, so `Effect.timeout` and interruption cancel the request.
- Every method is `Effect.fn("SuiCore.<method>")` so it has a span and the `Include` generic still flows. The same holds on `Sui`, with one exception: `getObject`, `getObjectOption`, `getObjects`, `getObjectsStrict`, `getDynamicFieldOption` and `getDynamicObjectFieldOption` declare overloads so that passing a `schema` narrows the result type, and `Effect.fn` cannot express an overload set. Their implementations are still `Effect.fn`; only the declared type is written out by hand.
- `mapSdkError` distinguishes a `SimulationError` that describes a transaction from one that is really a transport failure. The SDK's resolve plugin wraps *whatever went wrong* in a `SimulationError`, a rejected fetch and a gRPC `UNAVAILABLE` included; only a wrapper carrying an `executionError` is `SimulationFailed`. One whose `cause` chain classifies as transport (a gRPC status name, an HTTP status number, an abort, a bare `fetch` `TypeError`) is a `TransportError` with that cause's status and retryability.
- One `mapSdkError` function turns SDK failures into the taxonomy in section 10; per-method unions are derived from it:
  - `getObject`: `ObjectNotFound | ObjectDeleted | ObjectUnavailable | TransportError`
  - `getObjects`: `TransportError` (per-item errors are in the result array)
  - `getTransaction`, `waitForTransaction`: `TransactionNotFound | TransportError`
  - `simulateTransaction`: `SimulationFailed | TransportError`
  - everything else: `TransportError`
- Read methods retry `TransportError` where `retryable` is true on `Schedule.min([exponential("250 millis"), spaced("10 seconds")]).pipe(Schedule.jittered)` capped at 5 attempts. `executeTransaction` is never retried at this tier. The retryable set is exactly: gRPC `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED`, `INTERNAL` and `UNKNOWN`; HTTP 5xx and 429; and timeouts. `INTERNAL` and `UNKNOWN` are in the set because they are how the transport reports that the request never reached a node at all: `@protobuf-ts/grpcweb-transport` turns a rejected `fetch` (connection refused, DNS failure) into `INTERNAL`, and its grpc-web format maps HTTP 500 to `UNKNOWN`. Without them a read against a node that is merely down or restarting is never retried. Every other status is an answer from the node and is not retried.
- Every read attempt is bounded by `requestTimeout` (`SuiCoreReadOptions`, on `layerGrpc`, `layerFromClient` and `makeFromClient`; default 30 seconds, `"Infinity"` off, `SUI_RPC_TIMEOUT` under `layerConfig`). An attempt that runs out is a retryable `TransportError { status: "DEADLINE_EXCEEDED" }`, so the read schedule above re-asks; the SDK's own `timeout` only sets a gRPC header and bounds nothing on a hung connection. `readRetry` replaces the schedule; each retry is logged at debug. Neither applies to `executeTransaction`, `signAndExecuteTransaction`, `waitForTransaction` or `use`. (0.4.0)
- An SDK error that is the **caller's** — a malformed filter, a function filter the SDK cannot paginate, `after` with `before` — is a defect, not a `TransportError`: retrying cannot fix it and reporting it as the node's failure hides the bug. (0.4.0)
- `getServiceInfo(): Effect<ServiceInfo, TransportError>` is gRPC's `LedgerService.GetServiceInfo` (`lowestAvailableCheckpoint` among it), which reconcile's pruning guard reads; other transports answer `UNIMPLEMENTED`. (0.4.0)
- `getObjectAtVersion({ objectId, version }): Effect<VersionedObject, TransportError>` is the one member that is **not** a wrap of a Core method, because the Core API has none: `GetObjectOptions` carries no version. It reaches the transport's own historical read — the gRPC `LedgerService.GetObject` with a `version`, JSON-RPC `sui_tryGetPastObject` — and answers `{ _tag: "Absent", reason }` on a transport that has neither, on a pruned version, and on a version that never existed. It exists for one caller: `Tx.reconcile` identifying which transaction consumed a version a set of bytes pinned (§6). `Absent` is never evidence.
- `use(f: (client: ClientWithCoreApi, signal: AbortSignal) => Promise<A>): Effect<A, SuiError>` is the low-level hatch for one-off calls into the SDK client object. It runs the same `mapSdkError`. There is no `raw` property; `use` is how a library built on this package reaches an upstream `$extend` package that needs the client object.
- Layers: `layerGrpc({ network, baseUrl, timeout?, mvr? })`, `layerFromClient(client)`, `layerConfig` (`SUI_NETWORK` required with no default, `SUI_RPC_URL` optional with a built-in default gRPC URL table because the SDK ships none), and `ScriptedSuiCore.layer(script)` in `@unconfirmed/sui-effect/testing`, which provides both `SuiCore` and the `ScriptedSuiCore` handle a test drives it with (§13).

## 3. `Sui`: the convenience tier

`layerNoDeps: Layer<Sui, NetworkMismatch | TransportError, SuiCore>`; `layer = layerNoDeps` over `SuiCore.layerGrpc`. At build it calls `getChainIdentifier` once and records the answer on `Sui.chainId`. The test layer is **not** a static on `Sui`: `layerTest(script)` is a function in `@unconfirmed/sui-effect/testing` (`Sui.layerNoDeps` over `ScriptedSuiCore.layer(script)`), so nothing under `src/services/Sui.ts` depends on the testing module.

Whether it asserts is decided by one exported table, `KNOWN_CHAIN_IDS`, holding the genesis checkpoint digests observed on the live networks (`mainnet` `4btiuiMPvEENsttpZC7CZ53DruC3MAgfznDbASZ7DR6S`, `testnet` `69WiPg3DAQiwdxfncX6wYQ2siKwAe6L9BZthQea3JNMD`); the SDK ships no such table. When the client's network is in the table, a node reporting a different identifier fails the layer with `NetworkMismatch { expected, actual }`. `devnet`, `localnet` and custom networks are regenerated and have no fixed identifier, so nothing is asserted and the observed one is recorded. `layerNoDepsWith({ chainId })` pins any network and overrides the table.

Fixed include sets: objects always `content + owner + type + version + digest`; execute always `effects + events + balanceChanges + objectTypes`. Anything else is one `SuiCore` call away.

Decisions recorded:
- **`Sui` is positional; `SuiCore` takes the SDK's options objects.** `sui.getObject(id, { schema })` against `core.getObject({ objectId, include })`: the opinionated tier names its one or two required arguments, and the mechanical tier stays the SDK's own shape so its docs apply unchanged.
- `streamEvents` and `streamTransactions` page on `hasNextPage`, never on the item count: a scan-limited gRPC server answers a rarely-matching filter with short or empty pages that still have a next page. A transaction that applied and failed is a `Result` failure carrying its `ExecutionFailed`, because in a history it is an ordinary entry, not a failure of the read.
- **The ledger streams resume and tail.** `after`/`before` start a stream at a cursor; a reader that commits its cursor with its rows pages through `sui.core.listEvents` / `listTransactions`, whose pages carry `endCursor` (0.6.0 removed the `…Pages` streams: one obvious way, and it is the SDK's); `tail*` never ends, polls (1 second by default), retries a retryable error from the last cursor rather than from genesis, and — because a caught-up *filtered* page returns no cursor, and a pruning node then prunes past the last match — advances a filtered cursor to the unfiltered head when a page comes back empty — sound only when the head read and the filtered page reach one node (or nodes at the same height), so a filtered tail whose completeness matters runs against a single, sticky node; behind a load balancer the move can skip matches for good. A transaction `function` filter must be fully qualified (`pkg::module::function`): the SDK refuses to paginate a `pkg` or `pkg::module` filter past the first page, so the stream and tail readers refuse those up front, and one page of one is `sui.core.listTransactions`. A full `eventType` filter is normalized (gRPC refuses a short address). The SDK's `listX` is `streamX` here throughout (`listOwnedObjects`, `listCoins`, `listBalances`, `listDynamicFields`, `listEvents`, `listTransactions`). (0.4.0)
- **`{ affectedAddress }` lists a history in and out (0.5.0).** The SDK's `TransactionFilter` has only `sender` and `function`, which cannot find a transfer *to* an address. The gRPC ledger's `ListTransactions` has an `affectedAddress` predicate (the address owns an object after the transaction, owned one that was mutated, transferred, deleted or wrapped, or its address balance changed), present in the proto of every SDK in range (2.30 and 2.38 alike), which the SDK's `listTransactions` does not expose. The transaction streams and tails take `AffectedAddressFilter`; a page is the SDK's own page loop (fifty items, one look-ahead, the same `hasNextPage` and base64 watermark cursors, so `after`/`before`, ordering and a tail's head cursor are exactly the other filters') over the ledger service, reached through `SuiCore.use` and duck-typed, with a `digest`-only read mask, then one `getTransaction` per digest (eight at a time, ledger order kept). A digest pruned between the listing and the read is left out. A transport without the ledger service fails it with a non-retryable `TransportError { status: "UNIMPLEMENTED" }`: an outgoing-only answer under an "everything affecting me" name would be a silent lie. Proved on localnet (`test/live.localnet.test.ts`).
- **Pruning nodes forget fast.** A localnet keeps a few dozen checkpoints (observed: `lowestAvailableCheckpoint` 23 to 40 behind the head), so a history listing, `getTransaction` of anything older and the reconcile of an old journal entry go blind within seconds; reconcile already refuses to call a miss evidence when `lowestAvailableCheckpoint` says the window was pruned (§6). An application that wants an activity record outliving retention keeps one.
- **Display v1 is `null` on gRPC.** A `0x2::display::Display<T>` (v1) object is not rendered by a gRPC node: `include: { display: true }` answers `display: null` (observed on localnet). Only Display v2, held under the registry at `0xd`, renders, so a package that creates a v1 `Display` in `init` needs a second transaction, `0x2::display_registry::migrate_v1_to_v2<T: key>(&mut DisplayRegistry, Display<T>, &mut TxContext): (display_registry::Display<T>, DisplayCap<T>)`, then `display_registry::share` on the result and the cap kept by the publisher (the signature read off the framework on localnet). A publish recipe says so.
- A SuiNS lookup on a node without SuiNS (`UNIMPLEMENTED`, as localnet answers) is `None`. A package object's `content` is an empty `Uint8Array`, never `undefined`. (0.4.0)
- A node reply that does not decode is a `TransportError` whose `cause` is the `DecodeError { kind: "shape", issues }`, one representation everywhere.
- `getTransaction` on a historical transaction whose status is failed fails with `ExecutionFailed`, the same as `Tx.submit` and `Tx.reconcile`, so there is exactly one representation of an on-chain failure.
- `view` decodes return value `result` (default 0) of command `command` (default the last command) from `simulate` with `commandResults`, and `checksEnabled: false` so non-entry functions can be inspected. It accepts a bare `@mysten/bcs` `BcsType` as well as a `Schema.Codec`, because a Move **return value** has no struct tag: `view(recipe, bcs.Address)` needs no invented type. `opts.sender` is set with `setSenderIfNotSet` on both `view` and `simulate`, so a recipe that set its own sender wins and an omitted sender is the SDK's own zero-address default.
- `SuiObject<S>` carries `id`, `version`, `digest`, `type`, `owner` as a tagged union, `content: S`, and `ref: ObjectRef` for feeding the builder. `type` is `ObjectType`, a union of `StructTag` and the literal `package`: gRPC reports `package` for a Move package object, and a package is a readable object like any other. `Simulation.objectTypes` and `Executed.objectTypes` are plain strings for the same reason.

## 4. `Executed` and `Simulation`

A `Schema.Class` built from the execute include set: `digest`, `effects`, `events`, `balanceChanges`, `objectTypes`, `checkpoint?`, `timestampMs?`, and `sender?` (0.5.0: `Tx.submit`, `submitVia`, `resubmit`, `reconcile` given the signed bytes, and `run` fill it from the bytes; `Sui.getTransaction` and both `streamTransactions` listings fill it too: they ask for the execute include set plus `bcs` and read the sender out of the transaction's BCS (`transaction: true` would make the SDK's gRPC parse throw on every non-programmable transaction, and costs about three times the bytes: +776 against +2,184 for a `send_funds` on localnet); `SuiCore`'s include types are unchanged, and a transaction kind the SDK's BCS cannot parse has no `sender`; `fromPartial` keeps an envelope's). Accessors, each returning full refs `{ id, type, version, digest, owner }` so the next transaction can consume them, and each ignoring accumulator writes:

`eventsOf(codec, eventType?)` (every event whose type matches the codec's — or the given — type under `typeMatches`, decoded) and `expectEvent(codec, eventType?)` (exactly one, else `UnexpectedEffects`; a layout mismatch is `DecodeError`), and `expectPublished()` (`{ packageId, package, upgradeCap }` for a publish or an upgrade, else `UnexpectedEffects`) are 0.4.0. **After an upgrade an object and an event struct keep the type of the package that first defined them**: a v1 struct emitted by v2 code is still `ORIGINAL::module::T`, a struct added in v2 lives under the v2 id, and an abort's `location.package` is the latest id. `created(type?)`, `createdWhere(predicate)` (the direct replacement for the substring matching downstream repos hand-roll), `mutated(type?)`, `deleted()`, `wrapped()`, `packagesPublished()` (`PackageWrite` and `Created`, refs like every other accessor, `type` falling back to the literal `package`), `balanceChange(address, coinType): bigint` and `gasUsedTotal: bigint` (both are signed deltas, so neither is `Mist`, which is non-negative), and `expectCreated(type): Effect<ChangedRef, UnexpectedEffects>` for the one-result case.

**`Simulation` has the same accessors through the same implementation** (0.5.0). It is a `Schema.Class` with the fields it had as a `Schema.Struct` (`digest`, `effects`, `events`, `balanceChanges`, `objectTypes`, `commandResults`, `gasPaymentMocked`), and every accessor above — plus `transferred` — is one function over the fields the two share, which both classes delegate to, so a preview and the receipt it predicts can never disagree about what "created" means. A simulation assembled by hand is `new Simulation({ ... })`.

`transferred(type?)` (0.5.0, both classes) is the objects whose **owner changed**: an input that existed, an output that still exists under the same id (`idOperation: "None"`, an object write), and an input owner and output owner that differ by **kind and party** — `AddressOwner(a)`, `ObjectOwner(id)` (a dynamic object field's parent), `Shared`, `Immutable`, `ConsensusAddressOwner(a)` — never by version, so a transfer, a freeze, a move under a dynamic object field and a move between `AddressOwner` and `ConsensusAddressOwner` count, and a consensus object whose `startVersion` moved does not. Either side unknown (a reduced envelope, the `Unknown` variant) is not evidence and is left out; a created, deleted or wrapped object is not transferred. Each ref is the output side with `inputOwner` beside `owner`. A transferred object is also `mutated`.

**Why accumulator writes are skipped.** An `outputState: "AccumulatorWriteV1"` change is an address balance moving — `balance::send_funds`, gas from a balance, a fold's deposit — recorded against the node's accumulator object: no owner on either side, no entry in `objectTypes`, no version a builder could use, and no amount (observed on localnet, protocol 139: a five-coin fold's simulation is five `Deleted` coins and one bare `AccumulatorWriteV1`). Nobody holds it, so it is no person's created or mutated object; what it moved is in `balanceChanges`, netted per address — which is why a fold's balance changes show only the gas, and why `FoldBatch.amount` (§6) is what a fold moves.

`deleted()` covers both shapes the effects use for "this object is gone from where it was": a delete (`idOperation: "Deleted"`) and a **wrap**, which the SDK's effects converter represents as an input that existed, an output that does not, and no id operation at all (`"None"`). `wrapped()` returns just the second kind, for a caller that has to tell them apart — a wrapped object still exists inside its wrapper and can come back.

Every accessor returns a `ChangedRef { id, type?, version?, digest?, owner? }` rather than a full `ObjectRef`: the effects carry `id` always and the rest only sometimes (a deleted object has no output version, a change missing from the `objectTypes` join has no type), and inventing version `0`, an empty digest or an `Unknown` owner would hand the builder a reference that looks usable and is not. `objectRefOf(ref)` returns a full `ObjectRef` when every field is present and `undefined` otherwise. `sdkRefOf(ref)` returns the shape the **SDK builder** wants — `{ objectId, version: string, digest }` — because sui-effect's `ObjectRef` carries `id` and a `bigint` `version` and `Transaction#objectRef` accepts neither. It is for an address-owned or immutable object only: a **shared** object goes through `tx.sharedObjectRef({ objectId, initialSharedVersion, mutable })`, whose initial shared version is on `ref.owner.Shared.initialSharedVersion`, and a **receiving** object through `tx.receivingRef(...)`, which takes the same three fields; passing a shared object by `objectRef` produces bytes a validator rejects.

## 5. `Signer` is a value, not a service

A credential is data, and one process may hold two (a sponsor verifies a sender signature and signs as itself). `R = Signer` cannot say which one, so the signer is always an explicit parameter.

```ts
interface Signer { address: SuiAddress; scheme: SignatureScheme; maxEpoch?: bigint /* 0.5.0 */; alias?: SuiAddress /* 0.6.0 */; signTransaction(bytes): Effect<Signature, SigningError>; signPersonalMessage(bytes): Effect<Signature, SigningError> }
Signer.fromSdkSigner(signer)                                                  // any @mysten/sui/cryptography Signer: Keypair, PasskeyKeypair, Ledger, KMS
Signer.fromKeypair(kp)                                                        // a thin alias; a Keypair is an SDK Signer
Signer.ephemeral: Effect<Signer>
Signer.remote({ address, scheme, signTransaction, signPersonalMessage? }): Signer   // KMS, HSM, another process
Signer.fromSecretKey(secret, { scheme? }): Effect<Signer, KeyError>          // suiprivkey1… (MLDSA65 imported on demand), hex seed or bytes, copied
Signer.fromMnemonic(phrase, { scheme?, account?, path? }): Effect<Signer, KeyError>   // BIP-39 checked first, then the SDK's deriveKeypair
Signer.generateMnemonic(words?): Effect<Redacted<string>, KeyError>          // crypto.getRandomValues, not Random
Signer.derivationPath(scheme, account?): string
Signer.zkLogin({ address, ephemeralSigner, inputs, maxEpoch }): Effect<Signer, SigningError>   // signature assembly only
Signer.multisig(publicKey: MultiSigPublicKey, signers): Effect<Signer, KeyError>   // combined in member order (0.6.0, §14)
Signer.alias(address, signer): Signer                                         // signs AS address through its alias set (0.6.0, §14)
```

A `Signer` never exposes secret material, and every signer only signs: building, simulation, approval, the journal and submission are `Tx`'s (§6). `SignatureScheme` is the SDK's own type, re-exported, so it is exactly as wide as the installed SDK. A signer that refuses says why when it knows: `SigningError.reason` is `"expired"` (a `maxEpoch` that has passed or would pass before the bytes could land), `"rejected"` (a person or device said no) or `"unavailable"` (the signer cannot be reached, or cannot sign this kind of thing), `SigningFailureReason` from the root.

- **Keys the process holds.** `fromMnemonic` checks the word count, every word against the English list and the checksum before anything is derived — the SDK's `deriveKeypair` checks none, so a phrase one word off derives a valid, empty account — then derives with the SDK on the scheme's standard path (or an explicit one, checked against the scheme's shape and every level below 2^31). `fromSecretKey` reads a Bech32 key of any scheme the SDK has a keypair class for, a 64-digit hex seed or 32 bytes, and builds the keypair over a **copy** (the SDK's ECDSA keypairs keep a reference to the bytes they are given). A `KeyError` never quotes the input: the Bech32 decoder's own message carries the whole key, so it is dropped. Reading a key from the environment is `Config.Redacted("SUI_PRIVATE_KEY").pipe(Effect.flatMap(Signer.fromSecretKey))`. There is no lockable or wiping signer (0.5.0's `LockableSigner` and `Signer.scoped`): JavaScript cannot guarantee a wipe, and a signer that can stop working is a state machine every caller has to handle.
- **zkLogin is signature assembly.** Given the ephemeral signer, the proof (`ZkLoginSignatureInputs`) and the `maxEpoch` the proof was made for, each signature is the ephemeral signature wrapped with the proof by the SDK's `getZkLoginSignature`; `address` is checked against the proof (legacy and current derivations), and `@mysten/sui/zklogin` is imported on first use. The signer refuses bytes whose expiration cannot begin before an epoch past `maxEpoch` (`SigningError { reason: "expired" }`), and `Tx.run` keeps the window inside it (§6). Getting a proof and keeping a session are the application's.
- **Passkeys and wallets** are SDK signers: the SDK's `PasskeyKeypair` goes through `fromSdkSigner`; a wallet the application connects to signs bytes the application then submits through `Tx.attach` or `Signer.remote`.

Checking a signature someone else made is `Verify` (on `/tx`, `R = Sui`): `verifyTransactionSignature(bytes, signature, { address?, checkAddressAliases? })` and `verifyPersonalMessageSignature(message, signature, { address? })`, the SDK's `@mysten/sui/verify` with the client taken from `sui.core`, answering the public key. An invalid signature is `SigningError`; a zkLogin or multisig check that could not reach the node is `TransportError`, never a verdict.

## 6. `Tx`: the lifecycle as functions (all `R = Sui`)

A recipe is a synchronous `(tx: Transaction) => void`. Reads happen in the surrounding Effect before the recipe. The draft is therefore pure, replayable and free of `R`.


`Reconciled` is `{ _tag: "Executed", executed } | { _tag: "ExecutionFailed" | "NotApplied" | "SubmissionUnknown", error }`: one discriminator in one place, which the 0.1.0 shape (a bare `Executed` beside three tagged errors) did not have. `reconcileAll` answers only for entries that were unresolved; `Journal.get(digest)` is how a caller asks about one that already settled (0.6.0 removed `Tx.recorded`, which was exactly that).

`submit` carries `TransportError` for exactly one status: gRPC `INVALID_ARGUMENT` **on the first send**, the node refusing the request outright, where nothing was executed and reconciling would ask whether a never-sent transaction is on chain. The `Signed` entry is then settled as `NotApplied { evidence: "refused" }`, so it is not left unresolved until its epoch window closes. After a timeout or a retryable failure a refusal says nothing about the earlier send, which may have landed, so it reconciles. Every other transport failure after the bytes may have gone out is still `SubmissionUnknown`.

`submitVia` is `submit` for a submission a third party makes: the `Signed` journal entry before the call, one call, the reply decoded into an `Executed` when it carries one, and `reconcile`'s evidence rules on an ambiguous failure. A `send` error whose instance declares `outcome: "not_applied"` fails through without a reconcile, and its entry is settled as `NotApplied { evidence: "refused" }`.

`submit` and `run` carry `NotApplied` because `submit` runs `reconcile` when its retries are exhausted, and proving that a transaction never applied is one of the three answers `reconcile` can give. `run` carries `TransportError` because `build` does: reads before the bytes exist can fail the ordinary way. Once bytes may have been sent, no `TransportError` escapes.

`reconcile` takes the signed bytes, not only a digest, because the evidence rules need them: given a bare `Digest` there is nothing to reason about and an unknown transaction is always `SubmissionUnknown` (with no `signed` on it, since there is nothing to re-send).

Semantics:
- **Gasless stablecoin transfers use the SDK's canonical recipe.** `Tx.gaslessStablecoinTransfer` feeds `Transaction#balance({ type, balance })` to `0x2::balance::send_funds<T>` and sets no gas field itself. The gRPC and GraphQL SDK resolvers simulate, consult the current protocol configuration and set zero gas only for an eligible resolved PTB. No allowlist is embedded here. Nor is today's 0.01 minimum converted locally: protocol configuration stores a per-token minimum in base units, and a type string does not carry trustworthy decimals. The mandatory build simulation is the authority; an application with verified metadata may reject a too-small display amount earlier.
- **Building always simulates.** On gRPC the SDK resolve plugin calls `simulateTransaction` with checks enabled during `build` and throws `SimulationError` on execution failure, which `Tx.build` maps to `SimulationFailed`. But the resolver **returns early** for a transaction that is already fully resolved — every input resolved, gas price, budget and payment set — and then nothing simulates at all, so a fully resolved `Tx.run` could sign and submit a transaction that was never checked. And only the gRPC plugin simulates whenever it runs: the core resolver every other transport uses (`coreClientResolveTransactionPlugin`) simulates only inside `setGasBudget`, which returns at once when the budget is preset, so a recipe that calls `tx.setGasBudget(...)` on JSON-RPC or GraphQL is resolved and never shown to execute. `Tx.build` asks, against the client that resolves and before it builds, whether the SDK will simulate — `false` when nothing resolves (the SDK's `needsTransactionResolution`, mirrored), `true` on gRPC, otherwise whether the budget is unset — and when the answer is no, runs one explicit `simulateTransaction` with checks enabled afterwards. So simulate-before-submit is unconditional on every transport: it costs nothing extra when the SDK simulated, and one call otherwise. The resolver's own reads go straight to the SDK under none of `SuiCore`'s retries, so `Tx.build` retries the whole resolver call on a retryable `TransportError` on `SuiCore`'s effective read policy, `core.readPolicy("use")` (the layer's `readRetry` when it was given one, else five attempts), each retry logged at debug and counted — nothing has been signed — and asks the simulate question afresh on each attempt.
- **A successful simulation has one digest even when gRPC omits the top-level copy.** `Sui.simulate` prefers `Transaction.digest`, falls back to `Transaction.effects.transactionDigest` when the top-level field is absent, and refuses the response as a non-retryable `TransportError` when both are present but disagree. Mainnet gRPC currently returns the fallback shape for gasless stablecoin resolution.
- **An interrupted build cancels the request it started, on every transport.** `BuildTransactionOptions` has no `signal`, and the resolver simulates through whatever client it is given, so an interrupted `Tx.build` used to end — releasing the sender lock — with a simulate still in flight. `Tx.build` hands the SDK a proxy client whose `core` methods inject the Effect's `AbortSignal`, which covers the base resolver (JSON-RPC, GraphQL) because it goes through `client.core.*`. The **gRPC** resolver does not: `GrpcCoreClient#resolveTransactionPlugin` closes over the private grpc client it was constructed with and calls `transactionExecutionService.simulateTransaction(request)` with no second argument, while every other method on that class passes `{ abort: options.signal }`. So on a gRPC client the plugin is rebuilt rather than delegated: `GrpcCoreClient` is public, and constructing one over a `SuiGrpcClient` whose `transactionExecutionService.simulateTransaction` adds `{ abort: signal }` — and whose `core` is the already-signalled proxy, for the resolver's own `getChainIdentifier`/`getCurrentSystemState` reads — yields the SDK's own plugin, line for line, with the signal attached. Nothing is re-implemented, and the cache is shared through `base`. `test/final-batch.test.ts` proves it at the transport: a recording `RpcTransport` under a real `SuiGrpcClient` sees `SimulateTransaction` carrying an `AbortSignal`, and that signal aborted when the build timed out.
- **Default expiration.** If the recipe did not set one, `Tx.build` sets `ValidDuring { minEpoch: epoch, maxEpoch: epoch + 1, minTimestamp: null, maxTimestamp: null, chain: chainId, nonce }`, where `epoch` comes from one `getCurrentSystemState` read and `nonce` from `SubmitConfig.nonce` (a `u32` from `Random` by default; see §7 for why a collision is not a second execution). `Built` and `Signed` also record `chain: sui.chainId`, which is what the chain-identity guard below reads for the expiration variants that name no chain. The epochs are not optional: the validator rule is that a transaction must either have address-owned inputs or a `ValidDuring` expiration of **at most two epochs**, so an unbounded expiration is rejected outright for a PTB whose only object inputs are shared, and for every `Tx.sponsored` transaction, which pays gas from an address balance and so has no gas coins either. Setting an expiration also suppresses the SDK resolver's own default, so nothing else will supply the epochs later. The SDK only defaults an expiration when a transaction has no owned inputs, so ours is set unconditionally. The `chain` field is a replay guard, and a live node enforces it: bytes signed for testnet cannot land on mainnet. `Signed` records the expiration.
- **No wall-clock bound by default.** `maxTimestamp` is `null` unless `SubmitConfig.validFor` is set, because **no Sui network accepts a timestamp expiration yet**: a devnet node refuses any transaction that carries one with `Feature is not supported: Timestamp-based transaction expiration is not yet supported`, whether or not epochs are set alongside it (verified live against `fullnode.devnet.sui.io`, epoch 91, by `test/live.devnet.test.ts`). `validFor` stays in `SubmitConfig` so a network that gains support needs no new API, and so the wall-clock rule in `reconcile` has something to read.
- **Submit never rebuilds.** `Tx.submit` writes `JournalEntry.Signed` before the first `executeTransaction`, retries only the identical bytes on retryable `TransportError` or timeout, and when retries exhaust runs `Tx.reconcile`. `TransportError` never escapes `submit` once bytes may have been sent. Since 0.4.0: a first-send **validator lock conflict** ("already locked by a different transaction", "rejected as invalid by more than 1/3 of validators") is reconciled up to three more times `reconcileRecheck` apart, because the winner may still be becoming visible; a `SubmissionUnknown` from a send names the send's own error; an answer for **another** digest — or a `submitVia` reply with no effects, or one reporting failure — is reconciled rather than returned; and the execute answer is journalled under `uninterruptibleMask`, so an interrupt cannot land between the answer and its record.
- **Re-sending is explicit.** `Tx.resubmit(signed | SubmissionUnknown)` sends the identical bytes again — safe, because identical bytes have one digest and execute once. It refuses when the journal already says `NotApplied`, and reconciles instead when the journal says `Executed`/`Failed`, when the bytes name another chain, or when their window has closed. The first-send `INVALID_ARGUMENT` refusal rule is off for it: earlier bytes may have landed. `Tx.reconcileAll({ resubmit: true })` re-sends every entry still `SubmissionUnknown` after reconciling.
- **Reconcile.** `getTransaction(digest)` found means `Executed` or `ExecutionFailed`. Not found may only become `NotApplied` on one of two kinds of evidence, and both are deliberately hard to obtain. (The third `NotAppliedEvidence`, `"refused"`, is never a reconcile answer: it is what `submit` and `submitVia` journal when the node or the service refused the first send.)
- **Chain identity first.** Before any recovery query, the chain the bytes were built for — `ValidDuring.chain` / `Validity.chain`, or the `chain` field `Tx.build` records for the variants that name none — is compared with `sui.chainId`. A mismatch is `SubmissionUnknown` naming both chains and nothing is asked, because a transaction still valid on chain A must never be declared expired by chain B's epoch. The journal's memory default is process-wide, which makes a mixed-network process exactly the case that would have done it.
- **Expiry is ordered and repeated, never a single observation.** That an expiration window has closed proves the bytes cannot execute *later*; it does not prove they did not execute *earlier*, and execution can happen between a lookup and an expiry check. The Core API offers no historical non-inclusion proof, so `NotApplied { evidence: "expired" }` requires, **in this order**: (a) `getCurrentSystemState` reporting an epoch strictly greater than the recorded `maxEpoch` (or `chainTime` past a recorded `maxTimestamp` by more than `expiryMargin`), then (b) a `getTransaction` miss, then (c) after `SubmitConfig.reconcileRecheck` (2 seconds by default, through the `Clock`) both (a) and (b) again. Any other order, or a single observation, yields `SubmissionUnknown`. `SubmitConfig.expiryEvidence: "never"` disables the rule outright, which is what a deployment behind a mixed-node load balancer sets. **Residual risk:** a node whose transaction index lags its epoch view can satisfy the rule twice for a transaction it has in fact executed; the recheck makes that unlikely, not impossible.

  Two vetoes since 0.4.0. **Positive evidence beats expiry**: the pinned references are read *before* the expiry rule, and a live object whose `previousTransaction` is this very digest means the transaction applied, so the answer is `SubmissionUnknown` (and `getTransaction` is asked again), never `expired`. **A pruning node cannot prove a miss**: on gRPC the rule reads `GetServiceInfo.lowestAvailableCheckpoint` and `GetEpoch(minEpoch).firstCheckpoint`, and when the node has pruned into the transaction's validity window a `getTransaction` miss is no evidence and the answer is `SubmissionUnknown` naming the pruned checkpoint. JSON-RPC and GraphQL report no history, so there the old rule stands and a deployment behind a pruning node sets `expiryEvidence: "never"`. `Tx.reconcile` journals its terminal answer for a digest the journal holds unresolved.
- **`inputConsumed` needs the consuming transaction's own `inputVersion`.** That an owned input has advanced is *not* evidence: the transaction being reconciled is itself the likeliest thing to have advanced it. Nor is the live object's `previousTransaction` by itself, which names the **latest** mutation — T can consume version 3 and U version 4, and the object then names U, so reconciling T against it would report `NotApplied` for a transaction that applied.

  There is **no `v + 1` rule**. Sui stamps every output of a transaction with that transaction's **Lamport version**, `max(input versions) + 1` across all of its inputs, so an owned object read alongside a newer gas coin goes from version 4 to 6,436,928 and the object "at version 5" never existed. (Observed live: a Clock-reading PTB moved a gas coin from version 4 to 6,436,928; `getObjectAtVersion(gas, 5)` was absent, and the old rule therefore produced `SubmissionUnknown` with `AppliedByUs` evidence one read away.) The rule is instead: for each pinned reference — an owned input **or a gas payment coin**, both of which the bytes pin — that has moved on or is gone, read the live object's `previousTransaction` and then:
  - it is **our** digest: the transaction applied; `getTransaction` is asked once more and answers `Executed` or `ExecutionFailed`, or `SubmissionUnknown` if the node still does not serve it;
  - it is a **different** digest: fetch **that** transaction with effects and find our object in its `changedObjects`. `inputVersion` **equal to the version these bytes pinned** means those exact bytes can never execute again, and that is the only thing `NotApplied { inputConsumed }` is ever built on. A **greater** `inputVersion` means something between the two consumed our version and the node does not serve the state in between, so nothing is proven. A transaction that **failed** on chain still consumed its inputs, so its effects are read out of `ExecutionFailed` as readily as out of `Executed`;
  - nothing readable — a deleted object, a node that names no transaction, a transaction the node has pruned: nothing is proven, never `NotApplied`.

  A **coin-reservation ref** in `gasData.payment` — the synthetic gas ref an address-balance payment uses — pins no object version and is not a pinned reference.

  The rule does not walk history, so it is conservative on hot objects: if V consumed the pinned version and W later consumed V's output, the live object names W, whose `inputVersion` is not the pinned one, and the answer is `SubmissionUnknown` rather than `NotApplied`.

  **Every pinned reference is tried** before the answer is `SubmissionUnknown`; the first inconclusive one is remembered and the next is read. `SuiCore.getObjectAtVersion` stays as a public primitive — it is the only way to read an object as it was — but it is no longer part of this rule. In practice `SubmissionUnknown`, not `NotApplied`, is what almost every stuck submission gets whose PTB touched a shared object or an owned object older than the gas coin; a deployment plans an operator or `reconcileAll` path for it.
- **No `TransportError` escapes reconcile either.** `Tx.reconcile` and `Tx.reconcileAll` convert every recovery read failure into `SubmissionUnknown { digest, signed?, cause }`. `SuiError.outcome` puts `TransportError` on `"not_applied"`, which about a submission that may have landed is the one answer that is never safe. Since 0.4.0 neither signature declares `TransportError`: it was never produced, and a declared-but-impossible tag invites a `catchTag` that handles nothing. In `Tx.reconcileAll` the failure settles **that entry** and the loop goes on, rather than aborting a whole startup on one unreachable read.

  `Tx.reconcileAll` settles every entry through `Tx.reconcile`, so the same rules apply at startup.
- **A transaction that pins nothing settles by expiry or by a re-send** (0.4.0). An address-balance transaction whose inputs are pure values, shared objects and withdrawals has no pinned reference, so `inputConsumed` can never be shown for it and the positive-evidence veto has nothing to read. Before its window closes every reconcile of it is `SubmissionUnknown` ("nothing proves it cannot land"); after, the ordered expiry rule decides. `Tx.resubmit` — the identical bytes — is the way out sooner, and `Tx.reconcileAll({ resubmit: true })` its startup form. Nothing in reconcile reads a version for such bytes; a coin-reservation ref is skipped the same way. An overdrawing lock-free transaction (§6, sender lock) is on chain as a failure, which reconcile reports as `ExecutionFailed` like any other.
- **Visibility before the lock is released.** Execute and indexing are two different operations: a transaction that executed is not necessarily one the next read or the next build's input resolution can see, and serializing per sender does not stop the second build resolving a gas coin the first one already spent. After a successful execute and **before** releasing the sender lock, `Tx.submit` calls `SuiCore.waitForTransaction({ digest })` bounded by `SubmitConfig.visibilityTimeout` (15 seconds). A wait that fails or times out **never changes the outcome**: the transaction executed, and the `Executed` stands. The miss is recorded as the `Tx.awaitVisible` span's `sui.visibility` attribute (`"visible"`, `"timeout"`, `"failed"`), the visibility-wait metric's `result`, and a log line with the digest at **debug** level (0.5.0; a warning before). Debug, because Effect's default logger writes to `console.log` — stdout — at the default minimum level `Info`, and the warning broke a `--json` CLI on a run whose outcome stood; the fact a caller can act on is already in the answer. A program that wants the line sets `References.MinimumLogLevel` to `Debug`. `SubmitConfig.awaitVisibility: false` turns it off.
- **The journal never changes an answer.** `JournalError` escapes `Tx.submit` only from the `Signed` write, which happens before the first `executeTransaction`: failing there is honest, because nothing has been sent. Once execute or reconcile has answered, a journal write that fails is logged with `Effect.logError` annotated with the digest and the outcome stands — reporting a charged `ExecutionFailed` as `JournalError` would put it on exit 4, "safe to retry", and invite a second submission.
- **A signer must match the bytes.** `Tx.sign` and `Tx.cosign` compare `signer.address` with the sender and the gas owner read back out of the bytes, and fail with `SigningError` when it is neither. Otherwise a misconfigured credential becomes a non-retryable `INVALID_ARGUMENT` from `executeTransaction`, which `Tx.submit` can only report as `SubmissionUnknown` for a transaction that never had a chance. A `Signer.remote` therefore has to report the address it signs as truthfully. A `Signer.alias` (0.6.0) is compared by the address it signs **as**; that its key is in that address's alias set is a chain read, which `Tx.run` makes before building and this offline check cannot (§14).
- **A sponsored `run` needs both signatures.** A transaction whose gas owner is not its sender is signed by both parties; one signature on such bytes is something a validator rejects outright. `Tx.run` takes `sponsor?: Signer` and co-signs with it. When `opts.gasOwner` differs from the signer's address and no `sponsor` is given, it fails with `SigningError` naming the missing address **before** anything is built; the same check runs again on the addresses read back out of the built bytes, so a recipe that set its own gas owner — which `Tx.sponsored` does — is caught too. A sponsor that signs elsewhere is a `Signer.remote` sponsor; two parties that cannot both sign in one process use the explicit lifecycle (`build` or `fromBytes`, `sign`, `attach` or `cosign`, `submit` or `submitVia`).
- **Sender lock: every build, and the submission only when the bytes pin something** (0.4.0). Two builds that overlap can resolve the same owned object or gas coin at the same version, and one of the two transactions then fails or equivocates. Bytes that pin no versioned object — gas from an address balance, inputs that are pure values, shared objects or `FundsWithdrawal`s — cannot race anything once they exist. So under `SubmitConfig.lockSender: "whenPinned"` (the default) `Tx.run` takes the sender lock for **every build**, and keeps it through signing, `onSigned` and submission **only when the built bytes pin** an owned or receiving input, or carry any gas payment ref at all — a gas coin or a coin-reservation ref. Otherwise it releases the lock before signing, and address-balance transactions from one sender sign, send and wait for visibility concurrently, serialized only for the length of a build. Builds stay serialized because whether bytes pin anything is known only once the resolver has chosen: `tx.coin(...)` resolves to coins when the balance does not cover it, and gas falls back to coins the same way, so a lock-free build would have to be thrown away and redone under the lock whenever the guess was wrong. The address whose coins may be spent is the **gas owner** when there is one, so when sender and gas owner differ both locks are taken, in ascending normalized-address order, so two runs needing the same pair cannot deadlock; the gas owner's is skipped when the recipe pays from an address balance (an explicit empty payment, which `Tx.sponsored` sets), so one sponsor serves many senders at once. `"always"` is the rule before 0.4.0 (the locks held from build through submit on every run); `"never"` takes none. `true`/`false` in `SubmitConfigOverrides` still mean `"always"`/`"never"`. The recipe is applied to a fresh `Transaction` before any lock is chosen, so a gas owner and a payment it sets itself are known; `opts.gasOwner` is not needed for them. `Tx.build` and `Tx.submit` called separately do not lock; `Tx.withSenderLock(address)` wraps them in the same lock. **The locks** (0.6.0: moved from `Sui` to `Tx`) are one `Semaphore(1)` per normalized address per `SuiCore` — the object every spread of a `Sui` shares — in a `WeakMap`, each entry reference-counted and deleted when nobody holds or waits for it: **per-key exclusion**, so two runs from one sender serialize and runs from different senders never wait on each other. `PartitionedSemaphore` is not that: it is one shared permit pool served round-robin by key. The in-flight registry of lock-free runs is keyed the same way. **A coin reservation holds the lock and waits for the balance to be quiet.** It is no versioned object, but the resolver gives a `tx.gas` user whose payer has a balance a reservation of that **whole** SUI balance as read at build time (`setGasPayment`: `addressBalance − withdrawals`), so any other spend from the balance that lands first makes the node refuse it at submission (`INVALID_ARGUMENT`, "Invalid withdraw reservation: Insufficient address balance") or execute it as `InsufficientFundsForWithdraw` (localnet, protocol 139: six of six concurrent `tx.splitCoins(tx.gas, …)` + `Tx.sendFunds` pairs from one folded account failed while reservations counted as pinning nothing). So it keeps the lock through submission, and a run whose recipe uses `tx.gas` first waits, under the lock, until no lock-free run is in flight on its payer, so the balance it reserves is the balance that will be there. Two residuals remain: a reservation that appears only after the build (a `tx.coin`/`tx.balance` intent that fell back to splitting `tx.gas`) holds the lock but does not wait for lock-free runs already in flight, and a `Tx.sponsored` run does not take its gas owner's lock, so it can still land between the gas owner's own `tx.gas` run's build and its execution. **Residual risk:** lock-free transactions from one sender can together withdraw more than the balance holds, and a gas budget counts in full against the balance, not the gas finally charged. When the shortfall already exists as the bytes are submitted the node refuses them (`INVALID_ARGUMENT`, settled as `NotApplied { evidence: "refused" }` while the `TransportError` escapes); when it arises between submission and execution the node executes the one that overdraws as a failure, `InsufficientFundsForWithdraw`, charging it no gas (observed on localnet, protocol 139, for both an overdrawing `FundsWithdrawal` and three 5,000,000-MIST budgets against a 13,000,000-MIST balance), which is `ExecutionFailed`: applied and final, and a new build may succeed once the balance allows. A flow that spends a balance down to zero sets `lockSender: "always"`.
- **Gas comes from the address balance by default** (0.4.0). An address balance has no object version, so a transaction paid from it pins no gas coin: it cannot equivocate one, two of them from one sender do not invalidate each other, and `Tx.run` need not serialize their submissions. Every SDK resolver already prefers it when the payment is left unset. The core resolver (`setGasPayment`; JSON-RPC and custom clients) pays from the payer's SUI address balance when the transaction does not use `tx.gas` and that balance covers the budget plus the payer's own SUI `FundsWithdrawal`s, and gRPC and GraphQL node-side gas selection do the same (verified on localnet, protocol 139: a payer holding coins **and** a sufficient balance gets `payment: []`). `tx.coin(...)` and `tx.balance(...)` draw from the balance first. So under `SubmitConfig.gasPayment: "preferAddressBalance"` (the default) `Tx.build` leaves an unset payment to the resolver and decides nothing itself; what the resolver chose is the span attribute `sui.gas_payment` (`"addressBalance"`, `"coinReservation"` or `"coins"`). **When the balance is insufficient the resolver falls back to coins**, a debug log names the payer and `Tx.foldCoins`, and the run follows the lock rule above. The fallback is deliberate rather than a `BuildError`: an account funded by a coin-paying faucet, a transfer or an exchange withdrawal holds coins until it folds them, and refusing all of its transactions by default would make the library unusable on its first day. `"requireAddressBalance"` makes the balance mandatory: an unset payment on a transaction that does not use `tx.gas` is pinned to `[]` before the build (so no coins are even listed), the check below applies to it, and a `tx.gas` user the resolver paid with coin objects fails with `BuildError` naming `Tx.foldCoins`. A payment the recipe set itself, an empty one included, is the recipe's choice under either policy. A transaction that uses `tx.gas` gets a **coin-reservation ref** — gas drawn from the balance through a synthetic coin, version `0` — ahead of any coins when the payer has a balance, and on gRPC with no coins at all the reservation alone (verified); a recipe that wants address-balance gas uses `tx.coin({ balance })` rather than `tx.splitCoins(tx.gas, …)`. `BuildTransactionOptions.assumeSufficientAddressBalances` (SDK 2.38, absent from the 2.28 floor's resolver) is not used: it saves the intent resolver's balance and coin reads, but turns an insufficient balance from a `BuildError` naming it into a failed simulate.
- **Address-balance gas is checked before signing.** An **explicit** empty payment — the recipe's (`Tx.sponsored` sets one) or `"requireAddressBalance"`'s — spends the payer's SUI address balance, which nothing in the build checks: a localnet node simulates an empty payment against an empty balance successfully and refuses the signed bytes at execution with `INVALID_ARGUMENT` "Insufficient address balance" (verified). `Tx.build` therefore reads that balance once, for an explicit empty payment only, and fails with `BuildError` when it is below the budget **plus the payer's own SUI withdrawals** (the `FundsWithdrawal` reservations drawn from the payer), the rule the SDK's resolver applies. A payment the resolver chose to leave empty is not read again: the resolver read the balance to choose it. Funding: the devnet/testnet V3 faucet (`requestSuiFromFaucetV3`) pays into the balance; the localnet V2 faucet, an ordinary transfer and an exchange withdrawal pay coins, which `Tx.foldCoins` deposits. **It also needs an epoch-bounded expiration**: a node refuses a transaction with neither an address-owned input nor a `ValidDuring` expiration of at most two epochs ("Transactions must either have address-owned inputs, or a ValidDuring expiration with at most two epochs of validity", verified on localnet for `None` and `Epoch`), so empty-payment bytes with no owned input whose expiration is not `ValidDuring`/`Validity` — `SubmitConfig.expiration: "epoch"`, or a recipe's own — are a `BuildError` before signing. The default expiration satisfies it. **And it cannot use `tx.gas`**: with an empty payment the gas coin is an empty coin, which the build simulation does not show — a node mocks a gas coin to simulate — and execution fails on, charging gas (`InsufficientCoinBalance in command 0`, verified on localnet), so empty-payment bytes that name `GasCoin` are a `BuildError` too; a recipe under `Tx.sponsored` or `"requireAddressBalance"` uses `tx.coin({ balance, useGasCoin: false })` or `Tx.sendFunds`. A resolver refusal (gRPC `INVALID_ARGUMENT`, `FAILED_PRECONDITION` or `NOT_FOUND`, or the SDK resolver's own error) is a `BuildError` with the node's message; a budget over `maxGasBudget` is `PolicyDenied { rule: "maxGasBudget" }`. (0.4.0)
- **Folding coins into the address balance** (0.4.0). `Tx.planFold({ owner, coinType?, maxCoinsPerTransaction? })` reads the owner's coin objects (of every coin type it holds coins of when `coinType` is omitted, SUI first), the SUI address balance and the reference gas price, and answers a `FoldPlan`: `batches`, each one transaction's coins, largest first, at most `maxCoinsPerTransaction` of them (default and maximum 500: one `MergeCoins` takes at most 511 arguments, a gas payment at most 256 coins), and `skipped`, SUI dust that cannot pay for its own fold. `Tx.fold(batch)` is the recipe for one batch; `Tx.foldCoins({ signer, coinType?, maxCoinsPerTransaction? })` plans for `signer.address` and runs the batches in order through `Tx.run`, answering `{ plan, executed }`. A preview is `Tx.build(Tx.fold(batch), { sender })` and `sui.simulate(built.bytes)`, with nothing signed; `batch.amount` is what moves into the balance.
  - **SUI pays for its own fold** (`gas: "foldedCoins"`). The batch is the gas payment (its first 256 coins; the rest are merged into the gas coin) and `0x2::coin::send_funds<SUI>(GasCoin, owner)` deposits the whole gas coin; the gas charge is settled against the balance. One transaction leaves **no SUI coin**, and it needs no address balance first, which is the bootstrap: a fresh faucet-funded account folds in one step. (Verified on localnet, protocol 139: five 200-SUI faucet coins became zero coins and 1,000.0039 SUI of balance; 290 coins folded in one transaction with a 0.155-SUI budget, net gas negative from the storage rebates.) A batch worth less than its estimated budget, `referenceGasPrice × (10,000 + 1,000 × coins)` MIST, cannot pay for itself; it is paid from the address balance instead (`gas: "addressBalance"`: the coins are inputs, the payment `[]`) when the balance projected after the earlier batches covers the estimate, and is skipped otherwise.
  - **Other coin types** (`gas: "auto"`): `MergeCoins` into the first coin, then `0x2::coin::send_funds<T>(coin, owner)`. The payment is left to the resolver, which pays from the SUI balance — funded by the SUI batches, which run first — or from SUI coins.
  - The coins are pinned at the versions the plan read (`tx.objectRef`), so every fold pins owned objects and runs under the sender lock. A coin that moved since planning fails that batch's build with `BuildError`; `Tx.foldCoins` stops at the first failure, and calling it again re-plans from what is left.
- **Sending into an address balance** (0.4.0). `Tx.sendFunds({ coinType?, amount, recipient })` is the canonical transfer: `0x2::balance::send_funds<T>(tx.balance({ type, balance }), recipient)`. The amount comes from the sender's balance when that covers it — no versioned input at all — and from coins otherwise, and the recipient receives a balance rather than a coin object it would have to fold.
- **Preflight.** `SubmitConfig.preflight`, when set, costs one extra simulate with effects and is where spend limits and target policies plug in. It fails with `PolicyDenied` only, so `Tx.run` stays typed.
- **What `Built` learned** (0.5.0). `built.gas` is read back out of the bytes by `Tx.build` and `Tx.fromBytes` alike: budget and price in MIST, `owner` (the payer: the gas owner, else the sender), the `payment` refs as the SDK spells them (`{ objectId, version, digest }`, a coin reservation included at version `0`), and `source`, the classification the 0.4.0 `sui.gas_payment` attribute already made (`"addressBalance"` for an empty payment, `"coinReservation"` when every ref is one, `"coins"` as soon as one is a coin). `built.simulation` is present **only when the build simulated exactly the returned bytes** — the explicit simulate of the rule above (the SDK did not simulate: a preset budget off gRPC, or nothing to resolve). On gRPC the resolver simulates the transaction before its budget is set, which is other bytes with another digest, so there is none, and a later step simulates once. `Tx.run`'s front half reuses `built.simulation` only when it is the very object `Tx.build` made in this process (a `WeakSet` of them, and its digest must be the one recomputed from `built.bytes`): a `Built` decoded from JSON may carry any `simulation` its author liked. Neither field reaches `Signed` or the journal (`Tx.sign` and `Tx.attach` copy named fields), and `gas` is **required**: a hand-built `Built` (which §6 has always said not to write) needs it; `Tx.fromBytes` fills it.
- **Approve before the first signature** (0.5.0). `Tx.run`'s `approve(prepared)` runs inside `finish(built)` after `preflight` — the same front half, so one simulate serves both — and before `Tx.sign`; giving it always costs that simulate. It succeeds to approve and fails with the caller's own error to refuse (a wallet's `UserRejected`), which `Tx.run`'s union carries as `E`: nothing signed, `onSigned` not run, nothing journalled (the journal is written by `Tx.submit`). It runs **where signing runs**: under the sender lock when the bytes pin an owned input or carry any gas payment ref, after the lock is released when they do not, so a person taking a minute over an address-balance send holds nobody's lock. A sponsored run approves the same way, `built.gasOwner` and `built.gas.owner` naming the sponsor; two parties that cannot sign in one process use the explicit lifecycle. `Prepared` is `{ built, simulation }`; there is no public `Tx.prepare` (0.6.0): a preview is `Tx.build` and `sui.simulate`, and a declared-intent check is the application's, written over `prepared.simulation` inside `approve`. `Tx.foldCoins({ plan, approve })` runs a previewed plan **as given** (not re-planned; a coin that moved fails its batch's build as any pinned input does; a plan for another owner — the plan's own or any batch's, since `fold(batch)` deposits into `batch.owner` — is a `BuildError` before anything runs) and calls `approve(prepared, batch)` per batch.
- **The `maxEpoch` bound** (0.5.0). A signer whose credential expires (`Signer.maxEpoch`: a zkLogin proof's) bounds the window the build sets. `Tx.build`'s `maxEpoch` caps the default `ValidDuring.maxEpoch` at `min(epoch + 1, maxEpoch)` and fails a bound below the current epoch before anything resolves, as `BuildError` whose `cause` is `SigningError { reason: "expired" }`; under `expiration: "none"` or a recipe's own expiration it costs one `getCurrentSystemState` to make that check, and the recipe's expiration is left as it is (a window past the bound only delays when `reconcile` can call a lost transaction expired: the signature itself stops being valid at the bound). `Tx.run` passes the earlier of `signer.maxEpoch` and `sponsor.maxEpoch` and reports the expired case as the `SigningError` itself. A one-epoch window (`maxEpoch` equal to the current epoch) is accepted by a node (localnet, `test/live.localnet.test.ts`).
- **A nonce outside the `u32` range fails the build.** `SubmitConfig.nonce` is a caller-supplied allocator and a value the wire cannot carry is a configuration mistake, not a transport failure: `Tx.build` fails with `BuildError` naming the value, so nothing puts it on the retry path.
- **Retry after not applied** is a documented idiom, not an API: wrap the whole `Effect.gen` block (reads plus `Tx.run`) in `Effect.retry({ while: (e) => SuiError.outcome(e) === "not_applied", times: 3 })`. Because `outcome(ExecutionFailed)` is `"applied"`, the idiom never re-runs a transaction that charged gas.
- `waitForCheckpoint` is deferred to phase 2.

## 7. `SubmitConfig` (`Context.Reference`, defaults shown)

`expiration: "validDuring" | "epoch" | "none"` (`"validDuring"`, which costs one `getCurrentSystemState` read per build for the epoch bounds), `validFor?: Duration` (unset; an *additional* `maxTimestamp`, which every Sui network refuses today), `maxGasBudget: Mist` (50 SUI, the protocol maximum; `Tx.build` fails with `PolicyDenied { rule: "maxGasBudget" }` when the budget the node chose is over it — `BuildError` before 0.4.0), `preflight?: (sim: Simulation) => Effect<void, PolicyDenied>` (none), `lockSender: "whenPinned" | "always" | "never"` (`"whenPinned"`: every build, and the submission only when the bytes pin a versioned object, §6; `true`/`false` as overrides mean `"always"`/`"never"`), `gasPayment: "preferAddressBalance" | "requireAddressBalance"` (`"preferAddressBalance"`; §6), `resubmit: Schedule` (jittered exponential, 30 second cap), `resubmitAttempts: number` (5), `executeTimeout: Duration` (60 seconds, after which one `executeTransaction` is treated as a retryable transport failure), `expiryMargin: Duration` (30 seconds of clock skew `Tx.reconcile` allows before calling a transaction expired), `expiryEvidence: "epochThenMiss" | "never"` (`"epochThenMiss"`; whether a closed expiration window may be evidence at all, §6), `reconcileRecheck: Duration` (2 seconds; the delay between the two observations that rule needs), `awaitVisibility: boolean` (true) and `visibilityTimeout: Duration` (15 seconds), which bound the `waitForTransaction` `Tx.submit` makes after a successful execute, and `nonce: Effect<number>` (a `u32` from `Random`).

`nonce` is what makes two otherwise identical address-balance transactions in one epoch different bytes with different digests. The default is process-local and does not survive a restart: independent 32-bit draws collide with probability about 1.16% after ten thousand such transactions. **A collision is not a second execution** — identical bytes have one digest and one journal key, so the second build *is* the first transaction; the failure mode is a transaction that can no longer be sent because its digest is taken, not a duplicated intent. A deployment that cares supplies a monotonic allocator that survives restarts (a counter in the store the journal uses, an id service); the value must be an integer in `[0, 2^32)` or the build fails. A journal-backed allocator is out of scope.

`SubmitConfig.with(overrides)` merges `overrides` over the config **in force** (0.4.0; it used to spread over the defaults, so a nested `with` silently reset an outer one), and `SubmitConfig.layer(overrides)` spreads over the defaults. Overrides (`SubmitConfigOverrides`) take `Duration.Input`, so `executeTimeout: "3 seconds"` typechecks. `awaitVisibility` delays every return of `Tx.submit`, with `lockSender: false` too: without it the caller's next read can miss the object.

`resubmitAttempts`, `executeTimeout` and `expiryMargin` are separate fields rather than constants because each is a number a test has to be able to drive and an operator has to be able to change: the attempt count is not expressible in a v4 `Schedule` that also has to be jittered, the timeout is what makes `Cause.TimeoutError` reachable at all, and the margin is the difference between "probably gone" and "provably gone".

## 8. `Journal` (`Context.Reference`, memory default)

Interface: `put(entry)`, `get(digest)`, `listUnresolved`. The memory default keeps `Journal` out of `R` and makes a one-shot script work with zero setup — and, because a `Context.Reference`'s default is computed once and cached on the reference, it is **process-wide**, so a test that submits provides `Journal.layerMemory` to stay isolated; for a script, the signed bytes inside `SubmissionUnknown` are the durable record (`describe` prints one line and never bytes; `SuiError.toJson` carries them). Because a `Context.Reference`'s identifier is `never` in v4 — which is exactly why it stays out of `R` — the layers that provide one are `Layer<never, ...>`; `Journal.layerMemory` is a fresh in-memory journal for a test or a process that wants its own, since the default value is computed once and cached on the reference.

**One key per entry, listed through `KeyValueStore.keys`, settled entries marked.** Each entry is one key (`entry:<digest>`, under the optional prefix), and nothing is read-modify-written, so there is nothing to lock: two journal instances, or two processes, over one prefix do not lose each other's entries. Since 0.5.0 a terminal entry carries a **settled marker** beside it (`settled:<digest>`, value the tag), and `listUnresolved` enumerates the keys once with `KeyValueStore.keys` (part of every store since effect 4.1, and why 4.1.1 is the floor), reads every entry key **without** a marker and keeps the unresolved ones, oldest first by `signedAt`/`at` — one `keys` and M reads for M unresolved entries, however many settled ones the store keeps, which is what makes the journal usable over a slow or remote store. The marker is a negative index: it names what may be skipped, never what must be read, so a missing marker costs a read and only a wrong one could hide an entry. The write order rules a wrong one out but for one window: a terminal `put` writes the entry, then the marker, then reads the entry back and removes the marker unless the read confirms a terminal entry; an unresolved `put` clears the marker, writes the entry, and clears it again (each clear a `has`, and a `remove` only when present); a listing that reads an unmarked terminal entry marks it the same way (mark, re-read, remove unless confirmed), best effort and never failing the listing. A single writer's crash at any write therefore leaves at worst an unmarked settled entry — one spurious read, after which it is marked — and the second clear and the re-read together keep a terminal put or a listing from hiding a `Signed`/`Unknown` put of the same digest racing it from another context (another process's `Tx.reconcileAll` writing `Unknown` for an entry this one is settling; before the review fix a terminal put had no re-read, and that race hid the entry). **The window**: a settling process that dies (or whose `remove` fails) after its marker write and before its re-read, while the other writer's whole `put` landed just before that marker write, leaves the marker over an unresolved entry — hidden from listings, never from `get`, until the digest is written again. Closing it needs a compare-and-set `KeyValueStore` does not offer. `pruneSettled(before, { prefix? })` deletes settled entries recorded before a cutoff (marker first, then entry; it reads every entry and deletes nothing on the strength of a marker alone) and sweeps markers whose entry is gone, and answers how many entries — never a `Signed` or `Unknown` one, however old; it is still what keeps `keys` short.

**Compatibility.** A store 0.4 wrote has entries and no markers and reads with no migration: an unmarked entry is always read, so its first listing is the 0.4 scan (and marks every settled entry it finds), the second reads only the unresolved ones. Rolling back to 0.4 is safe for 0.4 — it reads only `entry:` keys — **but rolling forward again after 0.4 wrote is not**: a 0.4 `put` of an unresolved entry over a digest 0.5 had settled leaves 0.5's marker, so before a 0.5 process lists that store again delete every `settled:` key (or drain the journal with `Tx.reconcileAll()` on 0.4). **A 0.4 writer beside a 0.5 one is not**, in one case: a 0.4 process that writes an unresolved entry over a digest 0.5 had settled (the same bytes submitted again) leaves the marker, and the entry is hidden from `listUnresolved` (not from `get`); stop 0.4 writers before mixing versions. A store a 0.3 journal wrote reads with no migration; its `index` key is ignored, left in place and no longer maintained. **Rolling back to 0.3 is not safe as is**: 0.3 lists unresolved entries only through that index, so a `Signed` or `Unknown` entry 0.4 or later wrote is invisible to a 0.3 `listUnresolved`, `Tx.reconcileAll` and `onUnresolved: "fail"` (only `Tx.recorded(digest)` finds it), and a 0.3 reader cannot decode a `NotApplied { evidence: "refused" }` entry, which 0.4 writes. Before rolling back, or while 0.3 and later processes share a store, drain it with `Tx.reconcileAll()` (or settle the entries by hand) and delete the `"refused"` entries.

`@unconfirmed/sui-effect/journal` provides `layerKeyValueStore({ onUnresolved: "fail" | "ignore", prefix? }): Layer<never, JournalError, KeyValueStore>`, `makeKeyValueStore(store, { prefix? })` and `pruneSettled(before, { prefix? })` as module-level functions, and re-exports the unchanged `Journal` reference. They are not statics on `Journal`: attaching them would mean mutating the one shared reference object at import time, which a package marked `sideEffects: false` is entitled to have dropped. Layer build does no network work beyond listing entries; an application that wants to reconcile at startup calls `Tx.reconcileAll: Effect<ReadonlyArray<Reconciled>, JournalError, Sui | Journal>` explicitly. This keeps the layer dependency direction simple and keeps network calls out of layer construction.

## 9. `JournalEntry` (`Schema.TaggedUnion`)

`Signed { digest, signed, signedAt }`, `Executed { digest, checkpoint?, at }`, `Failed { digest, reason, at }`, `NotApplied { digest, evidence, at }`, `Unknown { digest, signed, lastError, attempts, at }`, where `signed` is a `SignedTransaction { digest, bytes, signatures, sender, expiration? }` — one representation of signed bytes, shared with `SubmissionUnknown`, rather than the same five fields spelled out twice. `lastError` is the `SuiError.describe` line, so an entry is JSON with no error schema nested inside it. `checkpoint` and `SignedTransaction`'s `expiration`/`chain` are `Schema.optionalKey` (§10), so an entry either has the key with a value or does not have it — which is what JSON already gives a durable journal, so a line written before that rule decodes unchanged. `Signed` and `Unknown` are the unresolved tags; `Executed`, `Failed` and `NotApplied` are terminal. `NotApplied` is terminal and therefore a variant of its own: recording a proven-dead submission as `Unknown` would leave it unresolved in the durable journal forever, and `onUnresolved: "fail"` would refuse to build for the life of the store. This is the only place the lifecycle appears as a union; the program abstraction is the functions in section 6.

## 10. Errors

All `Schema.TaggedError` so they serialize. Flat tags, no inheritance.

**Every `?` field below is `Schema.optionalKey`, not `Schema.optional`**: on a shape this library constructs itself the key is either absent or carries a value its schema accepts, never present and set to `undefined` — the rule the Effect docs' "optional and default keys" page states, and the only one that reads as `status?: string` rather than `status?: string | undefined` under `exactOptionalPropertyTypes`. `Schema.optional` is kept exactly for the fields that mirror the SDK (`DynamicFieldEntry.childId`, `MoveLocation`, `CleverError`, `Event.json`, every `ExecutionReason` payload), where an object built by `@mysten/sui` really can carry a key with no value. Producers spread conditionally (`TransportError.fromUnknown`, `Executed.refOf`) rather than assigning `undefined`.

| Tag | Fields |
|---|---|
| `TransportError` | `method`, `retryable`, `status?`, `cause` (timeouts map here with `retryable: true`, `status: "DEADLINE_EXCEEDED"`) |
| `ObjectNotFound` / `ObjectDeleted` / `ObjectUnavailable` | `objectId`, `version?` (the three `ObjectError.reason` values) |
| `TransactionNotFound` | `digest` |
| `NetworkMismatch` | `expected`, `actual` |
| `DecodeError` | `objectId?`, `expectedType?`, `actualType?`, `kind: "type" \| "bytes" \| "shape"`, `issue` |
| `SimulationFailed` | `reason: ExecutionReason`, `message`, `command?` |
| `ExecutionFailed` | `digest`, `reason: ExecutionReason`, `command?`, `effects` |
| `SubmissionUnknown` | `digest`, `signed?`, `cause` (absent only when `Tx.reconcile` was given a bare digest, so there are no bytes to carry) |
| `NotApplied` | `digest`, `evidence: "expired" \| "inputConsumed" \| "refused"` |
| `SigningError` | `cause`, `reason?: "expired" \| "rejected" \| "unavailable"` (0.5.0, §5; `"locked"` removed in 0.6.0) |
| `BuildError` | `message`, `cause` (also a resolver refusal with the node's message, and an address balance below the budget plus withdrawals, coins chosen under `gasPayment: "requireAddressBalance"`, empty-payment bytes without an epoch-bounded expiration, and empty-payment bytes that use `tx.gas`) |
| `PolicyDenied` | `rule`, `message` (`preflight`, and the gas ceiling as `rule: "maxGasBudget"`) |
| `JournalError` | `cause` |
| `GraphQLUnavailable` | `method`, `reason` (what `SuiGraphQL.layerUnavailable` rejects every call with; outcome `not_applied`) |
| `UnexpectedEffects` | `digest`, `expected: string`, `found: ObjectId[]` (the ids that did match, so zero and many are told apart; `expected` is the string the caller asked for, because fabricating a valid `StructTag` from an invalid one is worse than repeating it). Outcome **`applied`**, exit **5**: it is built from an `Executed`, so the transaction reached the chain and gas was charged; only the receipt is missing |

`ExecutionReason` and `Owner` are `Schema.Union([...]).pipe(Schema.toTaggedUnion("$kind"))` rather than `_tag` unions, so the discriminant is the SDK's own `$kind` and our narrowing and the SDK's agree. `ExecutionReason` mirrors `SuiClientTypes.ExecutionError` exactly (`MoveAbort` with `abortCode: bigint`, `location`, `cleverError`; `SizeError`; `CommandArgumentError`; `TypeArgumentError`; `PackageUpgradeError`; `IndexError`; `CoinDenyListError`; `CongestedObjects`; `ObjectIdError`; `Unknown`, which carries the node's `message` and `command` since 0.4.0, because the gRPC parser reports `InsufficientCoinBalance`, `FunctionNotFound` and every kind without details as `Unknown` with the detail only in that sentence). Clever-error constant names are decoded automatically; a per-package abort registry is deferred.

Outside the taxonomy, `KeyError { reason, message }` — a refused phrase, secret key, derivation path or multisig member set (`invalidMnemonic`, `invalidSecretKey`, `invalidPath`, `unsupportedScheme`, `unavailable`, `invalidMultisig`) — **declares** `outcome: "not_applied"`, so `SuiError.outcome` places it with no special case.

`TransportError.fromUnknown(method, cause, retryable?)` is the constructor a library built on this package uses for its own network calls: it classifies `status` and `retryable` exactly as `SuiCore` does for the SDK's failures (gRPC status names, HTTP 5xx and 429, aborts and timeouts), so a hand-built `TransportError` never drifts from the library's.

`SignedTransaction` and `Built` carry `chain?: string`, the chain identifier `Tx.build` was run against, so the chain-identity guard in §6 works for the expiration variants (`Epoch`, `None`) that name no chain themselves.

`SuiError` is the union plus four helpers every repo hand-rolls today: `isRetryable(e)`, `outcome(e): "applied" | "not_applied" | "unknown"` (`applied` for `ExecutionFailed` and `UnexpectedEffects`, `unknown` for `SubmissionUnknown`, `not_applied` for every other tag **in the taxonomy**, and `unknown` for anything else that declares no `outcome` of its own), `describe(e, { tag? }): string` (one actionable line, for example `ExecutionFailed MoveAbort 0x..::escrow::claim EAlreadyClaimed "already claimed" (line 42) in command 1` — a clever abort names its constant, value and line and never the packed abort code; an `Unknown` reason prints the node's sentence, `SimulationFailed InsufficientCoinBalance in command 0`; `BuildError`, `SigningError`, `JournalError` and `SubmissionUnknown` append their cause's line; `DecodeError` kind `"type"` reads `object X is T1, expected T2`; a `ConfigError` reads `missing NAME`; never bytes, always one line; `{ tag: false }` drops the tag), and `toJson(e)`. Since 0.4.0 there are three more — `digestOf(e)`, `moveAbort(e): Option<MoveAbortInfo>` and `isMoveAbort(e, { package?, module?, function?, constant?, code? })`, the last two working on `SimulationFailed` and `ExecutionFailed` alike (after an upgrade an abort's `package` is the **latest** id, so match on `module`/`constant`) — and every helper takes `unknown`, so a Promise `catch` needs no cast.

## 11. Branded schemas and the BCS bridge

`SuiAddress`, `ObjectId`, `Digest`, `StructTag`, `CoinType`, `Signature`, `Mist` (`bigint`, for amounts that are always SUI: gas, budgets) as `Schema.String.pipe(Schema.check(...), Schema.brand(...))` with normalization on decode via `SchemaGetter.transform` (`normalizeSuiAddress`, `normalizeStructTag`). Since 0.4.0 the id decoders refuse `""`, a bare `0x` and non-hex (they used to pad them to the zero address), and `SuiAddress.Strict` / `ObjectId.Strict` decode a value a human typed — exactly 64 hex digits, `0x` optional, same brand — because padding turns a truncated paste into a different valid address. `.make` validates the padded form, `.normalize` (also on `CoinType` and `StructTag`) decodes a shorthand literal, and `CoinType.SUI` is the padded SUI type. `SuiSchema.name(codec, key)` / `SuiSchema.name(layout, type, key)` builds a `DynamicFieldName` from one description of the key. `SuiSchema.bcs(bcsType, expectedType?)` turns a `@mysten/bcs` `BcsType<T>` into `Schema.Codec<T, Uint8Array>` that decodes from `content` bytes only (never the transport-varying `json`). Since 0.5.0 `CoinType.Strict` decodes a coin type a person typed — exactly `0x<address>::<module>::<Name>`, type arguments allowed, same brand — refusing a bare symbol (`"USDC"`), surrounding whitespace, a package without `0x` and the coin object type `0x2::coin::Coin<…>` as a `SchemaError` in the error channel; `CoinType.normalize` keeps its contract (it throws, for literals a caller controls). And `Balance` and `Coin` amounts are `CoinAmount`, a plain non-negative `bigint` in the coin's own smallest unit: they were branded `Mist` for every coin, which claimed USDC base units were MIST. No symbol-to-type resolution: nothing on chain maps a symbol to a coin type, and coin metadata answers the other direction only.

**One type-matching rule, everywhere.** `typeMatches(expected, actual)` parses both with `parseStructTag`. When the expected tag carries **no type arguments** it names the generic itself and only `address::module::name` is compared, so `pkg::m::Composition` accepts `pkg::m::Composition<0x…::share::Share>` — which is what a node does with a bare type filter, and what makes one codec usable for a generic Move type. When the expected tag **carries** type arguments the two are compared in full after `normalizeStructTag`, so `Coin<0x2::sui::SUI>` matches its padded spelling and not `Coin<…::usdc::USDC>`. Anything that is not a struct tag (the literal `package`) compares as a normalized string. The object keeps its own instantiated type on `SuiObject.type`. The same function decides the `expectedType` option of `getObject` / `getObjectOption` / `getObjects`, the `actualType` check inside `SuiSchema.decode`, and the `type` filter of the scripted `SuiCore`'s `listOwnedObjects` (`/testing`), which would otherwise be stricter than a node.

`expectedType` is **optional**: a Move return value has no struct tag, so `SuiSchema.bcs(bcs.Address)` for a `Sui.view` carries none and nothing is compared. The re-serialize length check is still what rejects mis-shaped bytes. It must be a `BcsType`, not merely a `{ parse }` codec: the bridge re-serializes what it parsed to reject trailing bytes, which is what stops an `objectBcs` envelope from decoding as the struct it wraps (generated codegen output is a `BcsType`, so this costs nothing in practice). The expected type is stored as a schema annotation and read back by walking the encoding chain, so `SuiSchema.bcs(...).pipe(Schema.decodeTo(DomainClass, ...))` keeps the check; `getObject`, `getObjectOption` and `getObjects` also accept an explicit `expectedType` for codecs built some other way. A `Uint8Array` field that can reach an error or a journal entry (`SignedTransaction.bytes`) uses a base64 codec, so `SuiError.toJson` is JSON.

## 12. `SuiGraphQL`: one tag, no wrapper

sui-effect does not wrap the GraphQL API; an Effect-native GraphQL tier is out of scope. What it owns is the **tag**: `SuiGraphQL` is `Context.Service<SuiGraphQL, SuiGraphQLClient>()("@unconfirmed/sui-effect/SuiGraphQL")` over the SDK's own client, exported from the core subpath, so two libraries that both read GraphQL — and the application that configures the endpoint — agree on one client instead of each opening its own and each inventing a name for the failure.

- `SuiGraphQL.layer(client)` over a client the caller built.
- `SuiGraphQL.layerConfig` reads `SUI_GRAPHQL_URL` and `SUI_NETWORK` (the same variable `SuiCore.layerConfig` reads: an endpoint for one chain and a node for another is a misconfiguration no error can describe afterwards).
- `SuiGraphQL.layerUnavailable` (and `layerUnavailableWith(reason)`) provides a client whose every call rejects with `GraphQLUnavailable { method, reason }`. This is what an application with no endpoint provides: the absence becomes the failure the library already handles, at the call it would have made, instead of a layer that will not build.

- `SuiGraphQL.query(run, method?)` is that mapping, once: it yields the client, runs one call in `Effect.tryPromise`, passes a `GraphQLUnavailable` through unchanged and turns anything else into `TransportError.fromUnknown(method, cause)`. Its type is `Effect<A, GraphQLUnavailable | TransportError, SuiGraphQL>`, and `run` is `(client, signal) => Promise<A>`: the Effect's `AbortSignal`, to pass as the query's `signal`. Every library that read GraphQL was re-deriving those three lines and the passthrough was the part that got forgotten.

A library may still call `query` or `execute` inside its own `Effect.tryPromise` and map the rejection into its own union — `GraphQLUnavailable` as it is, or `TransportError.fromUnknown` for a call that reached the endpoint and failed.

## 13. Testing

Three kinds of test, and nothing that pretends to be a chain.

- **What a transaction does on chain, and what a validator accepts or refuses, is tested only against a real localnet**: the `test/live.localnet*.test.ts` suites, behind `SUI_LOCALNET=1` (`SUI_LOCALNET_URL`, `SUI_LOCALNET_FAUCET` override the endpoints), and one devnet proof of the default expiration behind `SUI_LIVE=1`. No code in the package or its tests simulates Move execution, balances, alias resolution or signature checks. The localnet suites prove address-balance gas and folding, concurrent lock-free sends, the expiration rule, identical-bytes re-sends landing once, `NotApplied { inputConsumed }` on the chain's own effects, a stale coin reservation refused, the sponsored flows (and a submission missing the sponsor's signature refused), the mnemonic and passkey signers, the zkLogin `maxEpoch` bound, the durable journal across processes, multisig member order and address aliases, and every recipe whose point is what a validator does.
- **Failure handling is tested with per-test stubs of the `SuiCore` methods involved**, each returning a scripted answer or fault: timeouts, transport errors, refusals before execution, `SubmissionUnknown`, resubmitting identical bytes, reconcile's evidence rules, the sender lock and its policies, the journal under faults and races. A stub replaces one method for one test (`{ ...core, getTransaction: … }` over a layer); there is no shared, stateful fake.
- **Pure code gets direct unit tests**, table-driven where cases repeat: the branded schemas, the BCS bridge and `typeMatches`, the error taxonomy and `SuiError.outcome`, `Executed`/`Simulation`, multisig ordering and validation, alias-object derivation, transaction shapes, `TestSchema.Asserts` round-trips of every error class and every `JournalEntry` variant, and the `TransportMethods` completeness type test.

`@unconfirmed/sui-effect/testing` gives consumers the same footing (0.6.0; it replaces `SuiCoreFake`):

- `ScriptedSuiCore.layer(script)` is `SuiCore` over an SDK `CoreClient` that answers from a `FakeScript` of plain values, so the production `SuiCore` (error mapping, read retries, request timeouts, spans) runs over it. It serves objects with their exact type and BCS bytes (`getObject`, `getObjects`, `listOwnedObjects` under `typeMatches`), the `0x2::coin::Coin<T>` objects among them as coins (`listCoins`, `getBalance`'s `coinBalance`), dynamic fields matched on the key's type (under `typeMatches`) and bytes (`getDynamicField`, `listDynamicFields`, `getDynamicObjectField`), address balances, the Clock object `0x6`, a fixed chain id, epoch and reference gas price, and — only when scripted — the next `executeTransaction` / `simulateTransaction` answers in order (`FakeOutcome.succeed`, `failWith`, `transportError`, `hang`; the last repeats), each stamped with the digest of the bytes it was handed; `getTransaction` serves an execute answer it gave. It never executes, applies or validates a transaction: an answer changes no object and no balance. Every other method dies naming itself. A build runs the SDK's own core resolver over these reads; a Move call whose object inputs need `getMoveFunction` is not scripted.
- `layerTest(script)` is `Sui.layerNoDeps` over it, with `testSubmitConfig` (a re-send schedule that does not wait) in force; a service built on `Sui` tests over `MyService.layer.pipe(Layer.provideMerge(layerTest(script)))`. `TestServices` names what it provides.
- `SuiTest` drives it from inside an Effect: `putObject`, `setClock`, `setAddressBalance`, `scriptExecute`, `scriptSimulate`, `calls` (every call received, for asserting what was sent), and `provide(layer)`, which adds a fresh `Journal.layerMemory` and `TestClock`, built locally. Fixtures: `fakeDigest(n)`, `fakeCoin({ … })` (a coin object with real BCS content), `transactionResultOf(digest, outcome)` (the SDK result a stub returns).

## 14. Address aliases and multisig signers (0.6.0)

Sui's address aliases (`0x2::address_alias`) let an address A authorize other addresses to sign transactions **as** A. `enable` (signed by A's own key) creates A's `AddressAliases` object — a derived object of the shared `AddressAliasState` at `0xa`, key `AliasKey(A)`, party-owned by A — holding the set `[A]`; `add`, `remove` and `replace_all` edit it (1 to 8 members, each edit signed as A by any current member); there is no disable. Validators resolve aliases for a transaction's **sender and gas owner**: a signature by any member of the address's set covers it, and once the address has a set **only** a member does — A's own key too only while A is listed. Personal messages are never resolved through aliases. A Miso account is A whose only alias is a weighted multisig M of a passkey, a zkLogin key, a recovery phrase and a watchdog key.

```ts
AddressAlias.aliasesId(address): ObjectId                                         // derived from 0xa at AliasKey(address)
AddressAlias.getAliases(address): Effect<AddressAliases, ObjectUnavailable | DecodeError | TransportError, Sui>
AddressAliases = { _tag: "NotEnabled", address } | { _tag: "Enabled", address, id, version, aliases }
AddressAlias.allows(aliases, signer): boolean                                     // pure
AddressAlias.requireSigner(address, signer): Effect<AddressAliases, PolicyDenied | TransportError, Sui>   // rule "alias.signer"
AddressAlias.enable() / add({ address, alias }) / remove({ address, alias }) / replaceAll({ address, aliases }): Recipe
Signer.multisig(publicKey: MultiSigPublicKey, signers: ReadonlyArray<Signer>): Effect<Signer, KeyError>   // reason "invalidMultisig"
Signer.alias(address, signer): Signer                                             // { address, alias: signer.address, … }
Verify.verifyTransactionSignature(bytes, signature, { address, checkAddressAliases: true }): Effect<PublicKey, SigningError | PolicyDenied | TransportError, Sui>
```

**The sender is the account; the alias only signs.** `Signer.alias(A, m)` is a value whose `address` is A and whose `alias` is the address whose key signs. Everything in the lifecycle that is keyed on an address reads `signer.address`, so `Tx.run(recipe, { signer: Signer.alias(A, m) })` builds with sender A, takes **A's** sender lock (and registers its in-flight run on A), and its `Built.sender`, the journal's `SignedTransaction.sender`, `onSigned`'s `Signed` and `approve`'s `Prepared` all name A. The journal is keyed by digest and never held a signer's address; M appears only inside the signature, and as the span attribute `sui.signer_alias`. `Tx.foldCoins` takes the same signer and is A's for the same reason. A multisig member signer or M itself never names a lock: two runs for A through two different aliases serialize on A, which is the account whose objects and balance they race for.

**Checked against the object, before anything is built.** `Tx.run` (and a `sponsor` given as `Signer.alias(gasOwner, key)`) reads A's `AddressAliases` object once, before the build, and refuses a key the set does not list (or any key but A's own while A has not enabled aliases) with `PolicyDenied { rule: "alias.signer" }`: nothing is built, simulated, signed or journalled for it. A read the node cannot serve, or an object that does not decode, is a `TransportError` with that cause — the key was neither accepted nor refused. The read is of the **object**, never of transaction history: nodes prune transactions, so a check that depended on one would answer differently on different nodes. The set can change between the read and execution; the validator is the final word, and a key removed in between is an `INVALID_ARGUMENT` refusal at the first send, settled `NotApplied { evidence: "refused" }` (§6).

**Where each check is made, and what it costs.**

| Where | Alias read | A key outside the set |
|---|---|---|
| `Tx.run` with a `Signer.alias` (signer or sponsor) | one per alias signer, before the build | `PolicyDenied { rule: "alias.signer" }` |
| `Tx.run` with a plain signer | none | the node's refusal (`INVALID_ARGUMENT`) — e.g. A's own key after A removed itself |
| `Tx.sign`, `Tx.cosign` (`R = never`) | none: they compare the address the signer signs **as** with the bytes | `SigningError` only for an address the bytes do not name |
| `Tx.attach` | only for a signature by neither the sender nor the gas owner: their sets are read until one lists the signer | `PolicyDenied { rule: "alias.signer" }` (a `SigningError` before 0.6.0) |
| `Verify.verifyTransactionSignature(…, { address, checkAddressAliases: true })` | always one, even for the address's own key | `PolicyDenied { rule: "alias.signer" }` |
| `Verify.verifyTransactionSignature(…, { address })` | none: the 0.4.0 "made by this address's key" check, unchanged | `SigningError` |

`Tx.attach` skips the read for the sender's own signature to keep a sponsor's attach free of reads in the common case; the residual is the plain-signer row's (an address that removed itself is refused at submission). `Verify` with `checkAddressAliases` answers the question a validator answers, so it never skips. Its `PolicyDenied` is in the error union only under the literal `checkAddressAliases: true` (an overload set — like `Sui.getObject`'s, declared over an `Effect.fn` implementation).

**`@mysten/sui` has no alias-aware verification** (2.38: `@mysten/sui/verify` takes `{ address, client }` only, and `checkAddressAliases` does not exist), so the read is ours: `sui.getObjectOption(aliasesId(address), { schema })` over `SuiSchema.bcs(AddressAliases { id, aliases: VecSet<address> }, "0x2::address_alias::AddressAliases")`. `deriveObjectID` is in the whole peer range (2.28 on). The option is named `checkAddressAliases` so that an SDK option of that name, should one appear, is the one this wraps.

**`Signer.multisig` combines in member order.** The SDK's `MultiSigPublicKey.combinePartialSignatures` keeps the order it is handed and computes the bitmap from the keys; a validator pairs the n-th signature with the n-th set bit, so partial signatures in any other order are refused on chain ("Invalid sig for pk=…", verified on localnet) — and the SDK's own `MultiSigSigner` passes its signers' signatures in the order the signers were given. `Signer.multisig` matches each signer to a member by address (the rule `MultiSigSigner` uses), refuses a non-member, a second signer for one member and a combined weight below the threshold with `KeyError { reason: "invalidMultisig" }` (declared `not_applied`), sorts the signers by member index once, and signs **sequentially** in that order — a person sees one passkey prompt at a time. Members may be of any scheme the SDK combines: Ed25519, Secp256k1, Secp256r1, a passkey (the SDK's `PasskeyKeypair` through `Signer.fromSdkSigner`), `Signer.zkLogin` (the SDK keys a zkLogin partial signature by the non-legacy identifier of its address seed and issuer, so the member must sign as that derivation), `Signer.remote`. The multisig's `maxEpoch` is the earliest member's, so a zkLogin member's proof bounds the window `Tx.run` builds. Personal messages combine the same way (a multisig personal-message signature verifies as the multisig).

**`Signer.alias` signs transactions only.** Its `signPersonalMessage` fails with `SigningError { reason: "unavailable" }`: the alias's signature over a message verifies as the alias, never as A, and handing it out as A's would be a lie a verifier catches only if it checks. Given a signer whose address already is A it answers that signer unchanged; given an alias signer it re-targets the same key (`alias` is the key's address, never a chain of aliases — validators do not resolve aliases transitively).

**Where it is proved.** The unit suite proves the alias read, the check and member order locally — `Verify` checks a multisig of local-scheme members with no node, and reversing two partial signatures fails it — and the chain's side on a localnet, in `test/live.localnet-alias.test.ts` (behind `SUI_LOCALNET=1`): `enable` creates the object at `AddressAlias.aliasesId(A)`, `add(M)` + `remove(A)` in one transaction, `Tx.run` with `Signer.alias(A, Signer.multisig(…))` given two members out of order lands, the same two combined in the given order are refused by the validator, `Tx.build` → sign → `Tx.attach` → `Tx.submit` lands, and A's old key is refused by the node and by `Verify` with `checkAddressAliases`. No zkLogin member signature reaches a validator here (no prover).

## 15. Out of scope

**Moved out in 0.6.0** (to the miso wallet's codebase, from git history): declared intents and their checks (`Intent`, `Verified`, `checkClaims`, `describeEffects`, `describeClaims`, `Tx.verify`) and the semantic screen (`Gate`, the Jev screen); the public `Tx.prepare`; account signers (`Signer.passkey`, `Signer.createPasskey`, `Signer.wallet`) and zkLogin session storage (`ZkLogin.save`/`load`/`remove`); the sealed keystore and the lockable signer (`Keystore`, `LockableSigner`, `Signer.scoped`); `KeyValueStore` layers over browser, React Native and extension storage; Enoki; `Tx.sendAll` and `Tx.foldMovement`; the `Script` preset; and the Promise face for SDK extensions (`SuiExtension`, `$extend`, the extension template and guide). Each was an application concern or a second way to do something the SDK or this package already does.

**Releasing the caller before visibility.** `Tx.submit` could answer as soon as execute answers and wait for visibility in the background. Not done: the sender lock is released only **after** the visibility wait, and that ordering is what makes the next build from the sender resolve the coin the last one produced.

**Not started.** gRPC subscriptions; an allowance recipe helper (`tx.balance({ allowance })` / `tx.withdrawal({ from: "allowance" })` are SDK pass-through); an in-process reservation ledger that would stop concurrent lock-free spends overdrawing one balance (§6, sender lock); a journal-backed nonce allocator; staking reads and recipes.
