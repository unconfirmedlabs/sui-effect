# @unconfirmed/sui-effect: v1 specification

Status: converged after a four-round adversarial design review on 2026-09-11 (`docs/debate-log.md`; research inputs in `docs/research/` — both in the repository, not the package). This document is the scope for the first implementation; anything not listed is deferred (section 14).

## 0. Purpose in one paragraph

@unconfirmed/sui-effect is an opinionated Effect v4 layer over `@mysten/sui` 2.x for building safe TypeScript applications and on-demand agent scripts on Sui. The SDK keeps doing BCS, transaction building, signing and transport. @unconfirmed/sui-effect owns the shape of the program around it: two client tiers, closed error unions on every function, the transaction lifecycle as functions with typed outcomes, crash-safe submission, and time, retry and interruption through Effect so tests can drive them. Every public name mirrors the SDK name it wraps so an agent that knows the SDK can guess @unconfirmed/sui-effect.

Three audiences, each with a stated entry point:

- **SDK authors** (our own downstream packages: onara, publish, m2m, future ones) build on `Sui` and `Tx` and ship an Effect service plus a derived Promise-facing client extension. Section 13 is their contract.
- **Script writers and agents** use `Script`, `Sui`, `Tx` and those SDK services directly, with full typed errors.
- **Promise consumers** (dapp-kit, third-party TypeScript) use the derived `$extend` registration on a plain SDK client and never see Effect.

`SuiCore` is the floor for all three. `Sui` and `Tx` are primarily the SDK author's toolkit; most consumer code will call an extension service, not `Sui`.

## 2. `SuiCore`: the mechanical tier

A hand-written 1:1 Effect wrap of `ClientWithCoreApi` from `@mysten/sui/client`.

- Every key of `SuiClientTypes.TransportMethods` is present, none optional on our side. A type-level test asserts `Exclude<keyof TransportMethods, keyof SuiCore["Service"]>` is `never`.
- `Include` generics are preserved exactly as the SDK declares them.
- Every call forwards the AbortSignal from `Effect.tryPromise((signal) => ...)` into `CoreClientMethodOptions.signal`, so `Effect.timeout` and interruption cancel the request.
- Every method is `Effect.fn("SuiCore.<method>")` so it has a span and the `Include` generic still flows. The same holds on `Sui`, with one exception: `getObject`, `getObjectOption`, `getObjects`, `getObjectsStrict`, `getDynamicFieldOption` and `getDynamicObjectFieldOption` declare overloads so that passing a `schema` narrows the result type, and `Effect.fn` cannot express an overload set. Their implementations are still `Effect.fn`; only the declared type is written out by hand.
- `mapSdkError` distinguishes a `SimulationError` that describes a transaction from one that is really a transport failure. The SDK's resolve plugin wraps *whatever went wrong* in a `SimulationError`, a rejected fetch and a gRPC `UNAVAILABLE` included; only a wrapper carrying an `executionError` is `SimulationFailed`. One whose `cause` chain classifies as transport (a gRPC status name, an HTTP status number, an abort, a bare `fetch` `TypeError`) is a `TransportError` with that cause's status and retryability.
- One `mapSdkError` function turns SDK failures into the taxonomy in section 10; per-method unions are derived from it:
  - `getObject`: `ObjectNotFound | ObjectDeleted | ObjectUnavailable | TransportError`
  - `getObjects`: `TransportError` (per-item errors are in the result array)
  - `getTransaction`, `waitForTransaction`: `TransactionNotFound | TransportError`
  - `simulateTransaction`: `SimulationFailed | TransportError`
  - everything else: `TransportError`
- Read methods retry `TransportError` where `retryable` is true on `Schedule.min([exponential("250 millis"), spaced("10 seconds")]).pipe(Schedule.jittered)` capped at 5 attempts. `executeTransaction` is never retried at this tier. The retryable set is exactly: gRPC `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED`, `INTERNAL` and `UNKNOWN`; HTTP 5xx and 429; and timeouts. `INTERNAL` and `UNKNOWN` are in the set because they are how the transport reports that the request never reached a node at all: `@protobuf-ts/grpcweb-transport` turns a rejected `fetch` (connection refused, DNS failure) into `INTERNAL`, and its grpc-web format maps HTTP 500 to `UNKNOWN`. Without them a read against a node that is merely down or restarting is never retried. Every other status is an answer from the node and is not retried.
- Every read attempt is bounded by `requestTimeout` (`SuiCoreReadOptions`, on `layerGrpc`, `layerFromClient` and `makeFromClient`; default 30 seconds, `"Infinity"` off, `SUI_RPC_TIMEOUT` under `layerConfig`). An attempt that runs out is a retryable `TransportError { status: "DEADLINE_EXCEEDED" }`, so the read schedule above re-asks; the SDK's own `timeout` only sets a gRPC header and bounds nothing on a hung connection. `readRetry` replaces the schedule; each retry is logged at debug. Neither applies to `executeTransaction`, `signAndExecuteTransaction`, `waitForTransaction` or `use`. (0.4.0)
- An SDK error that is the **caller's** — a malformed filter, a function filter the SDK cannot paginate, `after` with `before` — is a defect, not a `TransportError`: retrying cannot fix it and reporting it as the node's failure hides the bug. (0.4.0)
- `getServiceInfo(): Effect<ServiceInfo, TransportError>` is gRPC's `LedgerService.GetServiceInfo` (`lowestAvailableCheckpoint` among it), which reconcile's pruning guard reads; other transports answer `UNIMPLEMENTED`. (0.4.0)
- `getObjectAtVersion({ objectId, version }): Effect<VersionedObject, TransportError>` is the one member that is **not** a wrap of a Core method, because the Core API has none: `GetObjectOptions` carries no version. It reaches the transport's own historical read — the gRPC `LedgerService.GetObject` with a `version`, JSON-RPC `sui_tryGetPastObject` — and answers `{ _tag: "Absent", reason }` on a transport that has neither, on a pruned version, and on a version that never existed. It exists for one caller: `Tx.reconcile` identifying which transaction consumed a version a set of bytes pinned (§6). `Absent` is never evidence.
- `use(f: (client: ClientWithCoreApi, signal: AbortSignal) => Promise<A>): Effect<A, SuiError>` is the low-level hatch for one-off calls into the SDK client object. It runs the same `mapSdkError`. There is no `raw` property. Third-party `$extend` packages are not used directly from application code; each gets an Effect-native extension we maintain (section 13.3), and `use` is how that extension's implementation reaches the upstream package when it needs the client object.
- Layers: `layerGrpc({ network, baseUrl, timeout?, mvr? })`, `layerFromClient(client)`, `layerConfig` (`SUI_NETWORK` required with no default, `SUI_RPC_URL` optional with a built-in default gRPC URL table because the SDK ships none), and `SuiCoreFake.layer(script)` in `@unconfirmed/sui-effect/testing`, which provides both `SuiCore` and a `SuiCoreFake` handle a test drives it with.

## 3. `Sui`: the opinionated tier

`layerNoDeps: Layer<Sui, NetworkMismatch | TransportError, SuiCore>`; `layer = layerNoDeps` over `SuiCore.layerGrpc`. At build it calls `getChainIdentifier` once and records the answer on `Sui.chainId`. The test layer is **not** a static on `Sui`: `layerTest(script)` is a function in `@unconfirmed/sui-effect/testing` (`Sui.layerNoDeps` over `SuiCoreFake.layer(script)`), so nothing under `src/services/Sui.ts` depends on the fake.

`layerNoDepsPinned(chainId)` builds `Sui` **without** reading the chain identifier, taking the one it is given. It exists for `SuiExtension.fromService`'s `warm` option (13.2), which builds its runtime synchronously inside `register` and therefore cannot await a round trip. Nothing is asserted because nothing is asked; what still catches a node on the wrong chain is `Tx.build` stamping that id on the expiration, which a validator enforces.

Whether it asserts is decided by one exported table, `KNOWN_CHAIN_IDS`, holding the genesis checkpoint digests observed on the live networks (`mainnet` `4btiuiMPvEENsttpZC7CZ53DruC3MAgfznDbASZ7DR6S`, `testnet` `69WiPg3DAQiwdxfncX6wYQ2siKwAe6L9BZthQea3JNMD`); the SDK ships no such table. When the client's network is in the table, a node reporting a different identifier fails the layer with `NetworkMismatch { expected, actual }`. `devnet`, `localnet` and custom networks are regenerated and have no fixed identifier, so nothing is asserted and the observed one is recorded. `layerNoDepsWith({ chainId })` pins any network and overrides the table.

It owns one `Semaphore(1)` per sender address, kept in an `RcMap<address, Semaphore>` with a one minute idle time to live: **per-key exclusion**, so two runs from one sender serialize and runs from different senders never wait on each other. That is the right primitive, and `PartitionedSemaphore` (which effect 4 does ship) is not: it is one **shared** permit pool whose waiters are served round-robin by key — per-key fairness, not per-key exclusion — so with `permits: 1` every sender would serialize behind every other, and with more permits two runs from the same sender could hold permits at once. Reference counting is what keeps the pool bounded — whoever is inside the lock holds a reference, so a lock cannot be dropped while it is in use, and an idle one is released rather than sitting in a map for the life of the process.

Fixed include sets: objects always `content + owner + type + version + digest`; execute always `effects + events + balanceChanges + objectTypes`. Anything else is one `SuiCore` call away.

Decisions recorded:
- **`Sui` is positional; `SuiCore` takes the SDK's options objects.** `sui.getObject(id, { schema })` against `core.getObject({ objectId, include })`: the opinionated tier names its one or two required arguments, and the mechanical tier stays the SDK's own shape so its docs apply unchanged.
- `streamEvents` and `streamTransactions` page on `hasNextPage`, never on the item count: a scan-limited gRPC server answers a rarely-matching filter with short or empty pages that still have a next page. A transaction that applied and failed is a `Result` failure carrying its `ExecutionFailed`, because in a history it is an ordinary entry, not a failure of the read.
- **The ledger streams resume and tail.** `after`/`before` start a stream at a cursor; the `…Pages` variants yield `{ items, endCursor }` so a consumer commits the cursor in the same write as the items; `tail*` never ends, polls (1 second by default), retries a retryable error from the last cursor rather than from genesis, and — because a caught-up *filtered* page returns no cursor, and a pruning node then prunes past the last match — advances a filtered cursor to the unfiltered head when a page comes back empty — sound only when the head read and the filtered page reach one node (or nodes at the same height), so a filtered tail whose completeness matters runs against a single, sticky node; behind a load balancer the move can skip matches for good. A transaction `function` filter must be fully qualified (`pkg::module::function`): the SDK refuses to paginate a `pkg` or `pkg::module` filter past the first page, so the stream and tail readers refuse those up front, and one page of one is `sui.core.listTransactions`. A full `eventType` filter is normalized (gRPC refuses a short address). The SDK's `listX` is `streamX` here throughout (`listOwnedObjects`, `listCoins`, `listBalances`, `listDynamicFields`, `listEvents`, `listTransactions`). (0.4.0)
- A SuiNS lookup on a node without SuiNS (`UNIMPLEMENTED`, as localnet answers) is `None`. A package object's `content` is an empty `Uint8Array`, never `undefined`. (0.4.0)
- A node reply that does not decode is a `TransportError` whose `cause` is the `DecodeError { kind: "shape", issues }`, one representation everywhere.
- `getTransaction` on a historical transaction whose status is failed fails with `ExecutionFailed`, the same as `Tx.submit` and `Tx.reconcile`, so there is exactly one representation of an on-chain failure.
- `view` decodes return value `result` (default 0) of command `command` (default the last command) from `simulate` with `commandResults`, and `checksEnabled: false` so non-entry functions can be inspected. It accepts a bare `@mysten/bcs` `BcsType` as well as a `Schema.Codec`, because a Move **return value** has no struct tag: `view(recipe, bcs.Address)` needs no invented type. `opts.sender` is set with `setSenderIfNotSet` on both `view` and `simulate`, so a recipe that set its own sender wins and an omitted sender is the SDK's own zero-address default.
- `SuiObject<S>` carries `id`, `version`, `digest`, `type`, `owner` as a tagged union, `content: S`, and `ref: ObjectRef` for feeding the builder. `type` is `ObjectType`, a union of `StructTag` and the literal `package`: gRPC reports `package` for a Move package object, and a package is a readable object like any other. `Simulation.objectTypes` and `Executed.objectTypes` are plain strings for the same reason.

## 4. `Executed`

A `Schema.Class` built from the execute include set: `digest`, `effects`, `events`, `balanceChanges`, `objectTypes`, `checkpoint?`, `timestampMs?`. Accessors, each returning full refs `{ id, type, version, digest, owner }` so the next transaction can consume them, and each ignoring accumulator writes:

`eventsOf(codec, eventType?)` (every event whose type matches the codec's — or the given — type under `typeMatches`, decoded) and `expectEvent(codec, eventType?)` (exactly one, else `UnexpectedEffects`; a layout mismatch is `DecodeError`), and `expectPublished()` (`{ packageId, package, upgradeCap }` for a publish or an upgrade, else `UnexpectedEffects`) are 0.4.0. **After an upgrade an object and an event struct keep the type of the package that first defined them**: a v1 struct emitted by v2 code is still `ORIGINAL::module::T`, a struct added in v2 lives under the v2 id, and an abort's `location.package` is the latest id. `created(type?)`, `createdWhere(predicate)` (the direct replacement for the substring matching downstream repos hand-roll), `mutated(type?)`, `deleted()`, `wrapped()`, `packagesPublished()` (`PackageWrite` and `Created`, refs like every other accessor, `type` falling back to the literal `package`), `balanceChange(address, coinType): bigint` and `gasUsedTotal: bigint` (both are signed deltas, so neither is `Mist`, which is non-negative), and `expectCreated(type): Effect<ChangedRef, UnexpectedEffects>` for the one-result case.

`deleted()` covers both shapes the effects use for "this object is gone from where it was": a delete (`idOperation: "Deleted"`) and a **wrap**, which the SDK's effects converter represents as an input that existed, an output that does not, and no id operation at all (`"None"`). `wrapped()` returns just the second kind, for a caller that has to tell them apart — a wrapped object still exists inside its wrapper and can come back.

Every accessor returns a `ChangedRef { id, type?, version?, digest?, owner? }` rather than a full `ObjectRef`: the effects carry `id` always and the rest only sometimes (a deleted object has no output version, a change missing from the `objectTypes` join has no type), and inventing version `0`, an empty digest or an `Unknown` owner would hand the builder a reference that looks usable and is not. `objectRefOf(ref)` returns a full `ObjectRef` when every field is present and `undefined` otherwise. `sdkRefOf(ref)` returns the shape the **SDK builder** wants — `{ objectId, version: string, digest }` — because sui-effect's `ObjectRef` carries `id` and a `bigint` `version` and `Transaction#objectRef` accepts neither. It is for an address-owned or immutable object only: a **shared** object goes through `tx.sharedObjectRef({ objectId, initialSharedVersion, mutable })`, whose initial shared version is on `ref.owner.Shared.initialSharedVersion`, and a **receiving** object through `tx.receivingRef(...)`, which takes the same three fields; passing a shared object by `objectRef` produces bytes a validator rejects.

## 5. `Signer` is a value, not a service

A credential is data, and one process may hold two (onara verifies a sender signature and signs as sponsor). `R = Signer` cannot say which one, so the signer is always an explicit parameter.

```ts
interface Signer { address: SuiAddress; scheme: SignatureScheme; signTransaction(bytes): Effect<Signature, SigningError>; signPersonalMessage(bytes): Effect<Signature, SigningError> }
Signer.fromSdkSigner(signer)                                                  // any @mysten/sui/cryptography Signer: Ledger, wallet, KMS
Signer.fromKeypair(kp)                                                        // a thin alias; a Keypair is an SDK Signer
Signer.fromConfig(name = "SUI_PRIVATE_KEY"): Effect<Signer, ConfigError>     // Config.Redacted + decodeSuiPrivateKey + scheme dispatch (ML-DSA-65 imported on demand)
Signer.ephemeral: Effect<Signer>
Signer.remote(f): Signer                                                      // KMS or wallet
```

A `Signer` never exposes secret material. `SignatureScheme` is the SDK's own type, re-exported, so it is exactly as wide as the installed SDK.

Account signers — a zkLogin session, a passkey, an external wallet — are `Signer` values too, with stated lifetimes (`Signer.maxEpoch` for a session-bound one); §18.

Checking a signature someone else made is `Verify` (on `/tx`, `R = Sui`): `verifyTransactionSignature(bytes, signature, { address? })` and `verifyPersonalMessageSignature(message, signature, { address? })`, the SDK's `@mysten/sui/verify` with the client taken from `sui.core`, answering the public key. An invalid signature is `SigningError`; a zkLogin or multisig check that could not reach the node is `TransportError`, never a verdict. onara's sender check before it co-signs is the first one with `address: sender`.

## 6. `Tx`: the lifecycle as functions (all `R = Sui`)

A recipe is a synchronous `(tx: Transaction) => void`. Reads happen in the surrounding Effect before the recipe. The draft is therefore pure, replayable and free of `R`.

```ts
Tx.reconcileAll(opts?: { resubmit?: boolean }): Effect<ReadonlyArray<Reconciled>, JournalError>   // Reconciled is a Schema.TaggedUnion since 0.1.2; resubmit 0.4.0
```

`Reconciled` is `{ _tag: "Executed", executed } | { _tag: "ExecutionFailed" | "NotApplied" | "SubmissionUnknown", error }`: one discriminator in one place, which the 0.1.0 shape (a bare `Executed` beside three tagged errors) did not have. `reconcileAll` answers only for entries that were unresolved; `Tx.recorded` is how a caller asks about one that already settled.

`submit` carries `TransportError` for exactly one status: gRPC `INVALID_ARGUMENT` **on the first send**, the node refusing the request outright, where nothing was executed and reconciling would ask whether a never-sent transaction is on chain. The `Signed` entry is then settled as `NotApplied { evidence: "refused" }`, so it is not left unresolved until its epoch window closes. After a timeout or a retryable failure a refusal says nothing about the earlier send, which may have landed, so it reconciles. Every other transport failure after the bytes may have gone out is still `SubmissionUnknown`.

`submitVia` is `submit` for a submission a third party makes: the `Signed` journal entry before the call, one call, the reply decoded into an `Executed` when it carries one, and `reconcile`'s evidence rules on an ambiguous failure. A `send` error whose instance declares `outcome: "not_applied"` fails through without a reconcile, and its entry is settled as `NotApplied { evidence: "refused" }`.

`submit` and `run` carry `NotApplied` because `submit` runs `reconcile` when its retries are exhausted, and proving that a transaction never applied is one of the three answers `reconcile` can give. `run` carries `TransportError` because `build` does: reads before the bytes exist can fail the ordinary way. Once bytes may have been sent, no `TransportError` escapes.

`reconcile` takes the signed bytes, not only a digest, because the evidence rules need them: given a bare `Digest` there is nothing to reason about and an unknown transaction is always `SubmissionUnknown` (with no `signed` on it, since there is nothing to re-send).

Semantics:
- **Gasless stablecoin transfers use the SDK's canonical recipe.** `Tx.gaslessStablecoinTransfer` feeds `Transaction#balance({ type, balance })` to `0x2::balance::send_funds<T>` and sets no gas field itself. The gRPC and GraphQL SDK resolvers simulate, consult the current protocol configuration and set zero gas only for an eligible resolved PTB. No allowlist is embedded here. Nor is today's 0.01 minimum converted locally: protocol configuration stores a per-token minimum in base units, and a type string does not carry trustworthy decimals. The mandatory build simulation is the authority; an application with verified metadata may reject a too-small display amount earlier.
- **Building always simulates.** On gRPC the SDK resolve plugin calls `simulateTransaction` with checks enabled during `build` and throws `SimulationError` on execution failure, which `Tx.build` maps to `SimulationFailed`. But the resolver **returns early** for a transaction that is already fully resolved — every input resolved, gas price, budget and payment set — and then nothing simulates at all, so a fully resolved `Tx.run` could sign and submit a transaction that was never checked. And only the gRPC plugin simulates whenever it runs: the core resolver every other transport uses (`coreClientResolveTransactionPlugin`) simulates only inside `setGasBudget`, which returns at once when the budget is preset, so a recipe that calls `tx.setGasBudget(...)` on JSON-RPC or GraphQL is resolved and never shown to execute. `Tx.build` asks, against the client that resolves and before it builds, whether the SDK will simulate — `false` when nothing resolves (the SDK's `needsTransactionResolution`, mirrored), `true` on gRPC, otherwise whether the budget is unset — and when the answer is no, runs one explicit `simulateTransaction` with checks enabled afterwards. So simulate-before-submit is unconditional on every transport: it costs nothing extra when the SDK simulated, and one call otherwise. The resolver's own reads go straight to the SDK under none of `SuiCore`'s retries, so `Tx.build` retries the whole resolver call on a retryable `TransportError` on `SuiCore`'s effective read policy, `core.readPolicy("use")` (the layer's `readRetry` when it was given one, else five attempts), each retry logged at debug and counted — nothing has been signed — and asks the simulate question afresh on each attempt.
- **A successful simulation has one digest even when gRPC omits the top-level copy.** `Sui.simulate` prefers `Transaction.digest`, falls back to `Transaction.effects.transactionDigest` when the top-level field is absent, and refuses the response as a non-retryable `TransportError` when both are present but disagree. Mainnet gRPC currently returns the fallback shape for gasless stablecoin resolution.
- **An interrupted build cancels the request it started, on every transport.** `BuildTransactionOptions` has no `signal`, and the resolver simulates through whatever client it is given, so an interrupted `Tx.build` used to end — releasing the sender lock — with a simulate still in flight. `Tx.build` hands the SDK a proxy client whose `core` methods inject the Effect's `AbortSignal`, which covers the base resolver (JSON-RPC, GraphQL) because it goes through `client.core.*`. The **gRPC** resolver does not: `GrpcCoreClient#resolveTransactionPlugin` closes over the private grpc client it was constructed with and calls `transactionExecutionService.simulateTransaction(request)` with no second argument, while every other method on that class passes `{ abort: options.signal }`. So on a gRPC client the plugin is rebuilt rather than delegated: `GrpcCoreClient` is public, and constructing one over a `SuiGrpcClient` whose `transactionExecutionService.simulateTransaction` adds `{ abort: signal }` — and whose `core` is the already-signalled proxy, for the resolver's own `getChainIdentifier`/`getCurrentSystemState` reads — yields the SDK's own plugin, line for line, with the signal attached. Nothing is re-implemented, and the cache is shared through `base`. `test/final-batch.test.ts` proves it at the transport: a recording `RpcTransport` under a real `SuiGrpcClient` sees `SimulateTransaction` carrying an `AbortSignal`, and that signal aborted when the build timed out.
- **Default expiration.** If the recipe did not set one, `Tx.build` sets `ValidDuring { minEpoch: epoch, maxEpoch: epoch + 1, minTimestamp: null, maxTimestamp: null, chain: chainId, nonce }`, where `epoch` comes from one `getCurrentSystemState` read and `nonce` from `SubmitConfig.nonce` (a `u32` from `Random` by default; see §7 for why a collision is not a second execution). `Built` and `Signed` also record `chain: sui.chainId`, which is what the chain-identity guard below reads for the expiration variants that name no chain. The epochs are not optional: the validator rule is that a transaction must either have address-owned inputs or a `ValidDuring` expiration of **at most two epochs**, so an unbounded expiration is rejected outright for a PTB whose only object inputs are shared, and for every `Tx.sponsored` transaction, which pays gas from an address balance and so has no gas coins either. Setting an expiration also suppresses the SDK resolver's own default, so nothing else will supply the epochs later. The SDK only defaults an expiration when a transaction has no owned inputs, so ours is set unconditionally. The `chain` field is a replay guard, and a live node enforces it: bytes signed for testnet cannot land on mainnet. `Signed` records the expiration.
- **No wall-clock bound by default.** `maxTimestamp` is `null` unless `SubmitConfig.validFor` is set, because **no Sui network accepts a timestamp expiration yet**: a devnet node refuses any transaction that carries one with `Feature is not supported: Timestamp-based transaction expiration is not yet supported`, whether or not epochs are set alongside it (verified live against `fullnode.devnet.sui.io`, epoch 91, by `test/live.devnet.test.ts`). `validFor` stays in `SubmitConfig` so a network that gains support needs no new API, and so the wall-clock rule in `reconcile` has something to read.
- **Submit never rebuilds.** `Tx.submit` writes `JournalEntry.Signed` before the first `executeTransaction`, retries only the identical bytes on retryable `TransportError` or timeout, and when retries exhaust runs `Tx.reconcile`. `TransportError` never escapes `submit` once bytes may have been sent. Since 0.4.0: a first-send **validator lock conflict** ("already locked by a different transaction", "rejected as invalid by more than 1/3 of validators") is reconciled up to three more times `reconcileRecheck` apart, because the winner may still be becoming visible; a `SubmissionUnknown` from a send names the send's own error; an answer for **another** digest — or a `submitVia` reply with no effects, or one reporting failure — is reconciled rather than returned; and the execute answer is journalled under `uninterruptibleMask`, so an interrupt cannot land between the answer and its record.
- **Re-sending is explicit.** `Tx.resubmit(signed | SubmissionUnknown)` sends the identical bytes again — safe, because identical bytes have one digest and execute once. It refuses when the journal already says `NotApplied`, and reconciles instead when the journal says `Executed`/`Failed`, when the bytes name another chain, or when their window has closed. The first-send `INVALID_ARGUMENT` refusal rule is off for it: earlier bytes may have landed. `Tx.reconcileAll({ resubmit: true })` re-sends every entry still `SubmissionUnknown` after reconciling.
- **Reconcile.** `getTransaction(digest)` found means `Executed` or `ExecutionFailed`. Not found may only become `NotApplied` on one of two kinds of evidence, and both are deliberately hard to obtain. (The third `NotAppliedEvidence`, `"refused"`, is never a reconcile answer: it is what `submit` and `submitVia` journal when the node or the service refused the first send.)
- **Chain identity first.** Before any recovery query, the chain the bytes were built for — `ValidDuring.chain` / `Validity.chain`, or the `chain` field `Tx.build` records for the variants that name none — is compared with `sui.chainId`. A mismatch is `SubmissionUnknown` naming both chains and nothing is asked, because a transaction still valid on chain A must never be declared expired by chain B's epoch. The journal's memory default is process-wide, which makes a mixed-network process exactly the case that would have done it.
- **Expiry is ordered and repeated, never a single observation.** That an expiration window has closed proves the bytes cannot execute *later*; it does not prove they did not execute *earlier*, and execution can happen between a lookup and an expiry check. The Core API offers no historical non-inclusion proof, so `NotApplied { evidence: "expired" }` requires, **in this order**: (a) `getCurrentSystemState` reporting an epoch strictly greater than the recorded `maxEpoch` (or `chainTime` past a recorded `maxTimestamp` by more than `expiryMargin`), then (b) a `getTransaction` miss, then (c) after `SubmitConfig.reconcileRecheck` (2 seconds by default, through the `Clock`) both (a) and (b) again. Any other order, or a single observation, yields `SubmissionUnknown`. `SubmitConfig.expiryEvidence: "never"` disables the rule outright, which is what a deployment behind a mixed-node load balancer sets. **Residual risk:** a node whose transaction index lags its epoch view can satisfy the rule twice for a transaction it has in fact executed; the recheck makes that unlikely, not impossible.

  Two vetoes since 0.4.0. **Positive evidence beats expiry**: the pinned references are read *before* the expiry rule, and a live object whose `previousTransaction` is this very digest means the transaction applied, so the answer is `SubmissionUnknown` (and `getTransaction` is asked again), never `expired`. **A pruning node cannot prove a miss**: on gRPC the rule reads `GetServiceInfo.lowestAvailableCheckpoint` and `GetEpoch(minEpoch).firstCheckpoint`, and when the node has pruned into the transaction's validity window a `getTransaction` miss is no evidence and the answer is `SubmissionUnknown` naming the pruned checkpoint. JSON-RPC and GraphQL report no history, so there the old rule stands and a deployment behind a pruning node sets `expiryEvidence: "never"`. `Tx.reconcile` journals its terminal answer for a digest the journal holds unresolved.
- **`inputConsumed` needs the consuming transaction's own `inputVersion`.** That an owned input has advanced is *not* evidence: the transaction being reconciled is itself the likeliest thing to have advanced it. Nor is the live object's `previousTransaction` by itself, which names the **latest** mutation — T can consume version 3 and U version 4, and the object then names U, so reconciling T against it would report `NotApplied` for a transaction that applied.

  There is **no `v + 1` rule**. Sui stamps every output of a transaction with that transaction's **Lamport version**, `max(input versions) + 1` across all of its inputs, so an owned object read alongside a newer gas coin goes from version 4 to 6,436,928 and the object "at version 5" never existed. (Observed live: a Clock-reading PTB moved a gas coin from version 4 to 6,436,928; `getObjectAtVersion(gas, 5)` was absent, and the old rule therefore produced `SubmissionUnknown` with `AppliedByUs` evidence one read away.) The rule is instead: for each pinned reference — an owned input **or a gas payment coin**, both of which the bytes pin — that has moved on or is gone, read the live object's `previousTransaction` and then:
  - it is **our** digest: the transaction applied; `getTransaction` is asked once more and answers `Executed` or `ExecutionFailed`, or `SubmissionUnknown` if the node still does not serve it;
  - it is a **different** digest: fetch **that** transaction with effects and find our object in its `changedObjects`. `inputVersion` **equal to the version these bytes pinned** means those exact bytes can never execute again, and that is the only thing `NotApplied { inputConsumed }` is ever built on. A **greater** `inputVersion` means something between the two consumed our version and the node does not serve the state in between, so nothing is proven. A transaction that **failed** on chain still consumed its inputs, so its effects are read out of `ExecutionFailed` as readily as out of `Executed`;
  - nothing readable — a deleted object, a node that names no transaction, a transaction the node has pruned: nothing is proven, never `NotApplied`.

  A **coin-reservation ref** in `gasData.payment` — the synthetic gas ref an address-balance payment uses — pins no object version and is not a pinned reference.

  The rule does not walk history, so it is conservative on hot objects: if V consumed the pinned version and W later consumed V's output, the live object names W, whose `inputVersion` is not the pinned one, and the answer is `SubmissionUnknown` rather than `NotApplied`.

  **Every pinned reference is tried** before the answer is `SubmissionUnknown`; the first inconclusive one is remembered and the next is read. `SuiCore.getObjectAtVersion` stays as a public primitive — it is the only way to read an object as it was — but it is no longer part of this rule. In practice `SubmissionUnknown`, not `NotApplied`, is what almost every stuck submission gets whose PTB touched a shared object or an owned object older than the gas coin; a deployment plans an operator or `reconcileAll` path for it.
- **No `TransportError` escapes reconcile either.** `Tx.reconcile` and `Tx.reconcileAll` convert every recovery read failure into `SubmissionUnknown { digest, signed?, cause }`. `SuiError.outcome` puts `TransportError` on `"not_applied"` and `Script.exitCode` on 4, which about a submission that may have landed is the one answer that is never safe. Since 0.4.0 neither signature declares `TransportError`: it was never produced, and a declared-but-impossible tag invites a `catchTag` that handles nothing. In `Tx.reconcileAll` the failure settles **that entry** and the loop goes on, rather than aborting a whole startup on one unreachable read.

  `Tx.reconcileAll` settles every entry through `Tx.reconcile`, so the same rules apply at startup.
- **A transaction that pins nothing settles by expiry or by a re-send** (0.4.0). An address-balance transaction whose inputs are pure values, shared objects and withdrawals has no pinned reference, so `inputConsumed` can never be shown for it and the positive-evidence veto has nothing to read. Before its window closes every reconcile of it is `SubmissionUnknown` ("nothing proves it cannot land"); after, the ordered expiry rule decides. `Tx.resubmit` — the identical bytes — is the way out sooner, and `Tx.reconcileAll({ resubmit: true })` its startup form. Nothing in reconcile reads a version for such bytes; a coin-reservation ref is skipped the same way. An overdrawing lock-free transaction (§6, sender lock) is on chain as a failure, which reconcile reports as `ExecutionFailed` like any other.
- **Visibility before the lock is released.** Execute and indexing are two different operations: a transaction that executed is not necessarily one the next read or the next build's input resolution can see, and serializing per sender does not stop the second build resolving a gas coin the first one already spent. After a successful execute and **before** releasing the sender lock, `Tx.submit` calls `SuiCore.waitForTransaction({ digest })` bounded by `SubmitConfig.visibilityTimeout` (15 seconds). A wait that fails or times out **never changes the outcome**: the transaction executed, the failure is logged with the digest, and the `Executed` stands. `SubmitConfig.awaitVisibility: false` turns it off.
- **The journal never changes an answer.** `JournalError` escapes `Tx.submit` only from the `Signed` write, which happens before the first `executeTransaction`: failing there is honest, because nothing has been sent. Once execute or reconcile has answered, a journal write that fails is logged with `Effect.logError` annotated with the digest and the outcome stands — reporting a charged `ExecutionFailed` as `JournalError` would put it on exit 4, "safe to retry", and invite a second submission.
- **A signer must match the bytes.** `Tx.sign` and `Tx.cosign` compare `signer.address` with the sender and the gas owner read back out of the bytes, and fail with `SigningError` when it is neither. Otherwise a misconfigured credential becomes a non-retryable `INVALID_ARGUMENT` from `executeTransaction`, which `Tx.submit` can only report as `SubmissionUnknown` for a transaction that never had a chance. A `Signer.remote` therefore has to report the address it signs as truthfully.
- **A sponsored `run` needs both signatures.** A transaction whose gas owner is not its sender is signed by both parties; one signature on such bytes is something a validator rejects outright. `Tx.run` takes `sponsor?: Signer` and co-signs with it. When `opts.gasOwner` differs from the signer's address and no `sponsor` is given, it fails with `SigningError` naming the missing address **before** anything is built; the same check runs again on the addresses read back out of the built bytes, so a recipe that set its own gas owner — which `Tx.sponsored` does — is caught too. Two parties that cannot both sign in one process use the explicit lifecycle (`build`, `sign`, `cosign`, `submit`).
- **Sender lock: every build, and the submission only when the bytes pin something** (0.4.0). Two builds that overlap can resolve the same owned object or gas coin at the same version, and one of the two transactions then fails or equivocates. Bytes that pin no versioned object — gas from an address balance, inputs that are pure values, shared objects or `FundsWithdrawal`s — cannot race anything once they exist. So under `SubmitConfig.lockSender: "whenPinned"` (the default) `Tx.run` takes the sender lock for **every build**, and keeps it through signing, `onSigned` and submission **only when the built bytes pin** an owned or receiving input, or carry any gas payment ref at all — a gas coin or a coin-reservation ref. Otherwise it releases the lock before signing, and address-balance transactions from one sender sign, send and wait for visibility concurrently, serialized only for the length of a build. Builds stay serialized because whether bytes pin anything is known only once the resolver has chosen: `tx.coin(...)` resolves to coins when the balance does not cover it, and gas falls back to coins the same way, so a lock-free build would have to be thrown away and redone under the lock whenever the guess was wrong. The address whose coins may be spent is the **gas owner** when there is one, so when sender and gas owner differ both locks are taken, in ascending normalized-address order, so two runs needing the same pair cannot deadlock; the gas owner's is skipped when the recipe pays from an address balance (an explicit empty payment, which `Tx.sponsored` sets), so one sponsor serves many senders at once. `"always"` is the rule before 0.4.0 (the locks held from build through submit on every run); `"never"` takes none. `true`/`false` in `SubmitConfigOverrides` still mean `"always"`/`"never"`. The recipe is applied to a fresh `Transaction` before any lock is chosen, so a gas owner and a payment it sets itself are known; `opts.gasOwner` is not needed for them. `Tx.build` and `Tx.submit` called separately do not lock; documented. **A coin reservation holds the lock and waits for the balance to be quiet.** It is no versioned object, but the resolver gives a `tx.gas` user whose payer has a balance a reservation of that **whole** SUI balance as read at build time (`setGasPayment`: `addressBalance − withdrawals`), so any other spend from the balance that lands first makes the node refuse it at submission (`INVALID_ARGUMENT`, "Invalid withdraw reservation: Insufficient address balance") or execute it as `InsufficientFundsForWithdraw` (localnet, protocol 139: six of six concurrent `tx.splitCoins(tx.gas, …)` + `Tx.sendFunds` pairs from one folded account failed while reservations counted as pinning nothing). So it keeps the lock through submission, and a run whose recipe uses `tx.gas` first waits, under the lock, until no lock-free run is in flight on its payer, so the balance it reserves is the balance that will be there. Two residuals remain: a reservation that appears only after the build (a `tx.coin`/`tx.balance` intent that fell back to splitting `tx.gas`) holds the lock but does not wait for lock-free runs already in flight, and a `Tx.sponsored` run does not take its gas owner's lock, so it can still land between the gas owner's own `tx.gas` run's build and its execution. **Residual risk:** lock-free transactions from one sender can together withdraw more than the balance holds, and a gas budget counts in full against the balance, not the gas finally charged. When the shortfall already exists as the bytes are submitted the node refuses them (`INVALID_ARGUMENT`, settled as `NotApplied { evidence: "refused" }` while the `TransportError` escapes); when it arises between submission and execution the node executes the one that overdraws as a failure, `InsufficientFundsForWithdraw`, charging it no gas (observed on localnet, protocol 139, for both an overdrawing `FundsWithdrawal` and three 5,000,000-MIST budgets against a 13,000,000-MIST balance), which is `ExecutionFailed`: applied and final, and a new build may succeed once the balance allows. A flow that spends a balance down to zero sets `lockSender: "always"`.
- **Gas comes from the address balance by default** (0.4.0). An address balance has no object version, so a transaction paid from it pins no gas coin: it cannot equivocate one, two of them from one sender do not invalidate each other, and `Tx.run` need not serialize their submissions. Every SDK resolver already prefers it when the payment is left unset. The core resolver (`setGasPayment`; JSON-RPC and custom clients) pays from the payer's SUI address balance when the transaction does not use `tx.gas` and that balance covers the budget plus the payer's own SUI `FundsWithdrawal`s, and gRPC and GraphQL node-side gas selection do the same (verified on localnet, protocol 139: a payer holding coins **and** a sufficient balance gets `payment: []`). `tx.coin(...)` and `tx.balance(...)` draw from the balance first. So under `SubmitConfig.gasPayment: "preferAddressBalance"` (the default) `Tx.build` leaves an unset payment to the resolver and decides nothing itself; what the resolver chose is the span attribute `sui.gas_payment` (`"addressBalance"`, `"coinReservation"` or `"coins"`). **When the balance is insufficient the resolver falls back to coins**, a debug log names the payer and `Tx.foldCoins`, and the run follows the lock rule above. The fallback is deliberate rather than a `BuildError`: an account funded by a coin-paying faucet, a transfer or an exchange withdrawal holds coins until it folds them, and refusing all of its transactions by default would make the library unusable on its first day. `"requireAddressBalance"` makes the balance mandatory: an unset payment on a transaction that does not use `tx.gas` is pinned to `[]` before the build (so no coins are even listed), the check below applies to it, and a `tx.gas` user the resolver paid with coin objects fails with `BuildError` naming `Tx.foldCoins`. A payment the recipe set itself, an empty one included, is the recipe's choice under either policy. A transaction that uses `tx.gas` gets a **coin-reservation ref** — gas drawn from the balance through a synthetic coin, version `0` — ahead of any coins when the payer has a balance, and on gRPC with no coins at all the reservation alone (verified); a recipe that wants address-balance gas uses `tx.coin({ balance })` rather than `tx.splitCoins(tx.gas, …)`. `BuildTransactionOptions.assumeSufficientAddressBalances` (SDK 2.38, absent from the 2.28 floor's resolver) is not used: it saves the intent resolver's balance and coin reads, but turns an insufficient balance from a `BuildError` naming it into a failed simulate.
- **Address-balance gas is checked before signing.** An **explicit** empty payment — the recipe's (`Tx.sponsored` sets one) or `"requireAddressBalance"`'s — spends the payer's SUI address balance, which nothing in the build checks: a localnet node simulates an empty payment against an empty balance successfully and refuses the signed bytes at execution with `INVALID_ARGUMENT` "Insufficient address balance" (verified). `Tx.build` therefore reads that balance once, for an explicit empty payment only, and fails with `BuildError` when it is below the budget **plus the payer's own SUI withdrawals** (the `FundsWithdrawal` reservations drawn from the payer), the rule the SDK's resolver applies. A payment the resolver chose to leave empty is not read again: the resolver read the balance to choose it. Funding: the devnet/testnet V3 faucet (`requestSuiFromFaucetV3`) pays into the balance; the localnet V2 faucet, an ordinary transfer and an exchange withdrawal pay coins, which `Tx.foldCoins` deposits. **It also needs an epoch-bounded expiration**: a node refuses a transaction with neither an address-owned input nor a `ValidDuring` expiration of at most two epochs ("Transactions must either have address-owned inputs, or a ValidDuring expiration with at most two epochs of validity", verified on localnet for `None` and `Epoch`), so empty-payment bytes with no owned input whose expiration is not `ValidDuring`/`Validity` — `SubmitConfig.expiration: "epoch"`, or a recipe's own — are a `BuildError` before signing. The default expiration satisfies it. **And it cannot use `tx.gas`**: with an empty payment the gas coin is an empty coin, which the build simulation does not show — a node mocks a gas coin to simulate — and execution fails on, charging gas (`InsufficientCoinBalance in command 0`, verified on localnet), so empty-payment bytes that name `GasCoin` are a `BuildError` too; a recipe under `Tx.sponsored` or `"requireAddressBalance"` uses `tx.coin({ balance, useGasCoin: false })`. A resolver refusal (gRPC `INVALID_ARGUMENT`, `FAILED_PRECONDITION` or `NOT_FOUND`, or the SDK resolver's own error) is a `BuildError` with the node's message; a budget over `maxGasBudget` is `PolicyDenied { rule: "maxGasBudget" }`. (0.4.0)
- **Folding coins into the address balance** (0.4.0). `Tx.planFold({ owner, coinType?, maxCoinsPerTransaction? })` reads the owner's coin objects (of every coin type it holds coins of when `coinType` is omitted, SUI first), the SUI address balance and the reference gas price, and answers a `FoldPlan`: `batches`, each one transaction's coins, largest first, at most `maxCoinsPerTransaction` of them (default and maximum 500: one `MergeCoins` takes at most 511 arguments, a gas payment at most 256 coins), and `skipped`, SUI dust that cannot pay for its own fold. `Tx.fold(batch)` is the recipe for one batch; `Tx.foldCoins({ signer, coinType?, maxCoinsPerTransaction? })` plans for `signer.address` and runs the batches in order through `Tx.run`, answering `{ plan, executed }`. A preview is `Tx.build(Tx.fold(batch), { sender })` and then `Sui.simulate` of its bytes, with nothing signed.
  - **SUI pays for its own fold** (`gas: "foldedCoins"`). The batch is the gas payment (its first 256 coins; the rest are merged into the gas coin) and `0x2::coin::send_funds<SUI>(GasCoin, owner)` deposits the whole gas coin; the gas charge is settled against the balance. One transaction leaves **no SUI coin**, and it needs no address balance first, which is the bootstrap: a fresh faucet-funded account folds in one step. (Verified on localnet, protocol 139: five 200-SUI faucet coins became zero coins and 1,000.0039 SUI of balance; 290 coins folded in one transaction with a 0.155-SUI budget, net gas negative from the storage rebates.) A batch worth less than its estimated budget, `referenceGasPrice × (10,000 + 1,000 × coins)` MIST, cannot pay for itself; it is paid from the address balance instead (`gas: "addressBalance"`: the coins are inputs, the payment `[]`) when the balance projected after the earlier batches covers the estimate, and is skipped otherwise.
  - **Other coin types** (`gas: "auto"`): `MergeCoins` into the first coin, then `0x2::coin::send_funds<T>(coin, owner)`. The payment is left to the resolver, which pays from the SUI balance — funded by the SUI batches, which run first — or from SUI coins.
  - The coins are pinned at the versions the plan read (`tx.objectRef`), so every fold pins owned objects and runs under the sender lock. A coin that moved since planning fails that batch's build with `BuildError`; `Tx.foldCoins` stops at the first failure, and calling it again re-plans from what is left.
- **Sending into an address balance** (0.4.0). `Tx.sendFunds({ coinType?, amount, recipient })` is the canonical transfer: `0x2::balance::send_funds<T>(tx.balance({ type, balance }), recipient)`. The amount comes from the sender's balance when that covers it — no versioned input at all — and from coins otherwise, and the recipient receives a balance rather than a coin object it would have to fold.
- **Preflight.** `SubmitConfig.preflight`, when set, costs one extra simulate with effects and is where spend limits and target policies plug in. It fails with `PolicyDenied` only, so `Tx.run` stays typed.
- **Intent** (0.5.0). `Tx.run`'s `intent`, when given, puts the built bytes through `Tx.verify`'s checks before anything is signed, on the **same** simulate `preflight` uses (one extra simulate of exactly the built bytes for either or both; preflight first, then the claims, then the screen). It runs after the build exactly where signing runs: under the lock when the bytes pin something, after the lock is released when they do not, so it never widens a `whenPinned` lock. `Gate.requireIntent` makes it mandatory: a run that declares nothing fails with `PolicyDenied { rule: "intent.required" }` before the recipe is applied. Section 17.
- **A nonce outside the `u32` range fails the build.** `SubmitConfig.nonce` is a caller-supplied allocator and a value the wire cannot carry is a configuration mistake, not a transport failure: `Tx.build` fails with `BuildError` naming the value, so nothing puts it on the retry path.
- **Retry after not applied** is a documented idiom, not an API: wrap the whole `Effect.gen` block (reads plus `Tx.run`) in `Effect.retry({ while: (e) => SuiError.outcome(e) === "not_applied", times: 3 })`. Because `outcome(ExecutionFailed)` is `"applied"`, the idiom never re-runs a transaction that charged gas.
- `waitForCheckpoint` is deferred to phase 2.

## 7. `SubmitConfig` (`Context.Reference`, defaults shown)

`expiration: "validDuring" | "epoch" | "none"` (`"validDuring"`, which costs one `getCurrentSystemState` read per build for the epoch bounds), `validFor?: Duration` (unset; an *additional* `maxTimestamp`, which every Sui network refuses today), `maxGasBudget: Mist` (50 SUI, the protocol maximum; `Tx.build` fails with `PolicyDenied { rule: "maxGasBudget" }` when the budget the node chose is over it — `BuildError` before 0.4.0), `preflight?: (sim: Simulation) => Effect<void, PolicyDenied>` (none), `lockSender: "whenPinned" | "always" | "never"` (`"whenPinned"`: every build, and the submission only when the bytes pin a versioned object, §6; `true`/`false` as overrides mean `"always"`/`"never"`), `gasPayment: "preferAddressBalance" | "requireAddressBalance"` (`"preferAddressBalance"`; §6), `resubmit: Schedule` (jittered exponential, 30 second cap), `resubmitAttempts: number` (5), `executeTimeout: Duration` (60 seconds, after which one `executeTransaction` is treated as a retryable transport failure), `expiryMargin: Duration` (30 seconds of clock skew `Tx.reconcile` allows before calling a transaction expired), `expiryEvidence: "epochThenMiss" | "never"` (`"epochThenMiss"`; whether a closed expiration window may be evidence at all, §6), `reconcileRecheck: Duration` (2 seconds; the delay between the two observations that rule needs), `awaitVisibility: boolean` (true) and `visibilityTimeout: Duration` (15 seconds), which bound the `waitForTransaction` `Tx.submit` makes after a successful execute, and `nonce: Effect<number>` (a `u32` from `Random`).

`nonce` is what makes two otherwise identical address-balance transactions in one epoch different bytes with different digests. The default is process-local and does not survive a restart: independent 32-bit draws collide with probability about 1.16% after ten thousand such transactions. **A collision is not a second execution** — identical bytes have one digest and one journal key, so the second build *is* the first transaction; the failure mode is a transaction that can no longer be sent because its digest is taken, not a duplicated intent. A deployment that cares supplies a monotonic allocator that survives restarts (a counter in the store the journal uses, an id service); the value must be an integer in `[0, 2^32)` or the build fails. A journal-backed allocator is deferred (§15).

`SubmitConfig.with(overrides)` merges `overrides` over the config **in force** (0.4.0; it used to spread over the defaults, so a nested `with` silently reset an outer one), and `SubmitConfig.layer(overrides)` spreads over the defaults. Overrides (`SubmitConfigOverrides`) take `Duration.Input`, so `executeTimeout: "3 seconds"` typechecks. `awaitVisibility` delays every return of `Tx.submit`, with `lockSender: false` too: without it the caller's next read can miss the object.

`resubmitAttempts`, `executeTimeout` and `expiryMargin` are separate fields rather than constants because each is a number a test has to be able to drive and an operator has to be able to change: the attempt count is not expressible in a v4 `Schedule` that also has to be jittered, the timeout is what makes `Cause.TimeoutError` reachable at all, and the margin is the difference between "probably gone" and "provably gone".

## 8. `Journal` (`Context.Reference`, memory default)

Interface: `put(entry)`, `get(digest)`, `listUnresolved`. The memory default keeps `Journal` out of `R` and makes a one-shot script work with zero setup — and, because a `Context.Reference`'s default is computed once and cached on the reference, it is **process-wide**, so a test that submits provides `Journal.layerMemory` to stay isolated; for scripts, the signed bytes inside `SubmissionUnknown` are the durable record: `describe` prints one line and never bytes, and `Script.run` prints the digest and the base64 bytes (a `bytes:` line, or the unresolved entry's `entry:` JSON). Because a `Context.Reference`'s identifier is `never` in v4 — which is exactly why it stays out of `R` — the layers that provide one are `Layer<never, ...>`; `Journal.layerMemory` is a fresh in-memory journal for a test or a process that wants its own, since the default value is computed once and cached on the reference.

**One write per entry, listed through `KeyValueStore.keys`.** Each entry is one key (`entry:<digest>`, under the optional prefix) and a `put` is one `set`, so there is no write order to get wrong and nothing to lock: two journal instances, or two processes, over one prefix do not lose each other's entries. `listUnresolved` enumerates the keys with `KeyValueStore.keys` (part of every store since effect 4.1, and why 4.1.1 is the floor), reads each entry and keeps the unresolved ones, oldest first by `signedAt`/`at`. It is an O(n) scan over every entry, settled ones included, so `pruneSettled(before, { prefix? })` deletes settled entries recorded before a cutoff and answers how many — never a `Signed` or `Unknown` one, however old. A store a 0.3 journal wrote reads with no migration; its `index` key is ignored, left in place and no longer maintained. **Rolling back is not safe as is**: 0.3 lists unresolved entries only through that index, so a `Signed` or `Unknown` entry 0.4 wrote is invisible to a 0.3 `listUnresolved`, `Tx.reconcileAll` and `onUnresolved: "fail"` (only `Tx.recorded(digest)` finds it), and a 0.3 reader cannot decode a `NotApplied { evidence: "refused" }` entry, which 0.4 writes. Before rolling back, or while 0.3 and 0.4 processes share a store, drain it with `Tx.reconcileAll()` on 0.4 (or settle the entries by hand) and delete the `"refused"` entries.

`@unconfirmed/sui-effect/journal` provides `layerKeyValueStore({ onUnresolved: "fail" | "ignore", prefix? }): Layer<never, JournalError, KeyValueStore>`, `makeKeyValueStore(store, { prefix? })` and `pruneSettled(before, { prefix? })` as module-level functions, and re-exports the unchanged `Journal` reference. They are not statics on `Journal`: attaching them would mean mutating the one shared reference object at import time, which a package marked `sideEffects: false` is entitled to have dropped. Layer build does no network work beyond listing entries; an application that wants to reconcile at startup calls `Tx.reconcileAll: Effect<ReadonlyArray<Reconciled>, JournalError, Sui | Journal>` explicitly. This keeps the layer dependency direction simple and keeps network calls out of layer construction.

## 9. `JournalEntry` (`Schema.TaggedUnion`)

`Signed { digest, signed, signedAt }`, `Executed { digest, checkpoint?, at }`, `Failed { digest, reason, at }`, `NotApplied { digest, evidence, at }`, `Unknown { digest, signed, lastError, attempts, at }`, where `signed` is a `SignedTransaction { digest, bytes, signatures, sender, expiration? }` — one representation of signed bytes, shared with `SubmissionUnknown`, rather than the same five fields spelled out twice. `lastError` is the `SuiError.describe` line, so an entry is JSON with no error schema nested inside it. `checkpoint` and `SignedTransaction`'s `expiration`/`chain` are `Schema.optionalKey` (§10), so an entry either has the key with a value or does not have it — which is what JSON already gives a durable journal, so a line written before that rule decodes unchanged. `Signed` and `Unknown` are the unresolved tags; `Executed`, `Failed` and `NotApplied` are terminal. `NotApplied` is terminal and therefore a variant of its own: recording a proven-dead submission as `Unknown` would leave it unresolved in the durable journal forever, and `onUnresolved: "fail"` would refuse to build for the life of the store. This is the only place the lifecycle appears as a union; the program abstraction is the functions in section 6.

## 10. Errors

All `Schema.TaggedError` so they serialize. Flat tags, no inheritance.

**Every `?` field below is `Schema.optionalKey`, not `Schema.optional`**: on a shape this library constructs itself the key is either absent or carries a value its schema accepts, never present and set to `undefined` — the rule the Effect docs' "optional and default keys" page states, and the only one that reads as `status?: string` rather than `status?: string | undefined` under `exactOptionalPropertyTypes`. `Schema.optional` is kept exactly for the fields that mirror the SDK (`DynamicFieldEntry.childId`, `MoveLocation`, `CleverError`, `Event.json`, every `ExecutionReason` payload), where an object built by `@mysten/sui` really can carry a key with no value. Producers spread conditionally (`TransportError.fromUnknown`, `Executed.refOf`) rather than assigning `undefined`.

`ExecutionReason` and `Owner` are `Schema.Union([...]).pipe(Schema.toTaggedUnion("$kind"))` rather than `_tag` unions, so the discriminant is the SDK's own `$kind` and our narrowing and the SDK's agree. `ExecutionReason` mirrors `SuiClientTypes.ExecutionError` exactly (`MoveAbort` with `abortCode: bigint`, `location`, `cleverError`; `SizeError`; `CommandArgumentError`; `TypeArgumentError`; `PackageUpgradeError`; `IndexError`; `CoinDenyListError`; `CongestedObjects`; `ObjectIdError`; `Unknown`, which carries the node's `message` and `command` since 0.4.0, because the gRPC parser reports `InsufficientCoinBalance`, `FunctionNotFound` and every kind without details as `Unknown` with the detail only in that sentence). Clever-error constant names are decoded automatically; a per-package abort registry is deferred.

`TransportError.fromUnknown(method, cause, retryable?)` is the constructor an extension uses for its own network calls: it classifies `status` and `retryable` exactly as `SuiCore` does for the SDK's failures (gRPC status names, HTTP 5xx and 429, aborts and timeouts), so a hand-built `TransportError` never drifts from the library's.

`SignedTransaction` and `Built` carry `chain?: string`, the chain identifier `Tx.build` was run against, so the chain-identity guard in §6 works for the expiration variants (`Epoch`, `None`) that name no chain themselves.

`SuiError` is the union plus four helpers every repo hand-rolls today: `isRetryable(e)`, `outcome(e): "applied" | "not_applied" | "unknown"` (`applied` for `ExecutionFailed` and `UnexpectedEffects`, `unknown` for `SubmissionUnknown`, `not_applied` for every other tag **in the taxonomy**, and `unknown` for anything else — see 13.1), `describe(e, { tag? }): string` (one actionable line, for example `ExecutionFailed MoveAbort 0x..::escrow::claim EAlreadyClaimed "already claimed" (line 42) in command 1` — a clever abort names its constant, value and line and never the packed abort code; an `Unknown` reason prints the node's sentence, `SimulationFailed InsufficientCoinBalance in command 0`; `BuildError`, `SigningError`, `JournalError` and `SubmissionUnknown` append their cause's line; `DecodeError` kind `"type"` reads `object X is T1, expected T2`; a `ConfigError` reads `missing NAME`; never bytes, always one line; `{ tag: false }` drops the tag), and `toJson(e)`. Since 0.4.0 there are three more — `digestOf(e)`, `moveAbort(e): Option<MoveAbortInfo>` and `isMoveAbort(e, { package?, module?, function?, constant?, code? })`, the last two working on `SimulationFailed` and `ExecutionFailed` alike (after an upgrade an abort's `package` is the **latest** id, so match on `module`/`constant`) — and every helper takes `unknown`, so a Promise `catch` needs no cast.

## 11. Branded schemas and the BCS bridge

`SuiAddress`, `ObjectId`, `Digest`, `StructTag`, `CoinType`, `Signature`, `Mist` (`bigint`) as `Schema.String.pipe(Schema.check(...), Schema.brand(...))` with normalization on decode via `SchemaGetter.transform` (`normalizeSuiAddress`, `normalizeStructTag`). Since 0.4.0 the id decoders refuse `""`, a bare `0x` and non-hex (they used to pad them to the zero address), and `SuiAddress.Strict` / `ObjectId.Strict` decode a value a human typed — exactly 64 hex digits, `0x` optional, same brand — because padding turns a truncated paste into a different valid address. `.make` validates the padded form, `.normalize` (also on `CoinType` and `StructTag`) decodes a shorthand literal, and `CoinType.SUI` is the padded SUI type. `SuiSchema.name(codec, key)` / `SuiSchema.name(layout, type, key)` builds a `DynamicFieldName` from one description of the key. `SuiSchema.bcs(bcsType, expectedType?)` turns a `@mysten/bcs` `BcsType<T>` into `Schema.Codec<T, Uint8Array>` that decodes from `content` bytes only (never the transport-varying `json`).

**One type-matching rule, everywhere.** `typeMatches(expected, actual)` parses both with `parseStructTag`. When the expected tag carries **no type arguments** it names the generic itself and only `address::module::name` is compared, so `pkg::m::Composition` accepts `pkg::m::Composition<0x…::share::Share>` — which is what a node does with a bare type filter, and what makes one codec usable for a generic Move type. When the expected tag **carries** type arguments the two are compared in full after `normalizeStructTag`, so `Coin<0x2::sui::SUI>` matches its padded spelling and not `Coin<…::usdc::USDC>`. Anything that is not a struct tag (the literal `package`) compares as a normalized string. The object keeps its own instantiated type on `SuiObject.type`. The same function decides the `expectedType` option of `getObject` / `getObjectOption` / `getObjects`, the `actualType` check inside `SuiSchema.decode`, and the `type` filter of `SuiCoreFake.listOwnedObjects`, which would otherwise be stricter than a node.

`expectedType` is **optional**: a Move return value has no struct tag, so `SuiSchema.bcs(bcs.Address)` for a `Sui.view` carries none and nothing is compared. The re-serialize length check is still what rejects mis-shaped bytes. It must be a `BcsType`, not merely a `{ parse }` codec: the bridge re-serializes what it parsed to reject trailing bytes, which is what stops an `objectBcs` envelope from decoding as the struct it wraps (generated codegen output is a `BcsType`, so this costs nothing in practice). The expected type is stored as a schema annotation and read back by walking the encoding chain, so `SuiSchema.bcs(...).pipe(Schema.decodeTo(DomainClass, ...))` keeps the check; `getObject`, `getObjectOption` and `getObjects` also accept an explicit `expectedType` for codecs built some other way. A `Uint8Array` field that can reach an error or a journal entry (`SignedTransaction.bytes`) uses a base64 codec, so `SuiError.toJson` is JSON.

## 12. `Script` preset (`@unconfirmed/sui-effect/script`)

- `Script` is a `Context.Service` `{ sui: Sui, core: SuiCore, signer: Signer, network }`. `Script.layer` reads `SUI_NETWORK` (required, no default; `mainnet` refused unless `SUI_ALLOW_MAINNET=1`), `SUI_RPC_URL` (optional), `SUI_PRIVATE_KEY` (a Bech32 `suiprivkey1…` or a 32-byte hex seed, `Config.Redacted`), and provides `Sui` and `SuiCore` alongside `Script`, so `Tx.*` works inside a script with no further wiring. `Script.layerReadOnly` provides a separate service, `ScriptReadOnly`, whose shape has no `signer`: one service cannot have two shapes, and a script written against `Script` must not silently build over a layer that cannot sign. `Script.layerNoDeps`, `Script.layerWithSigner(signer)` and `Script.layerReadOnlyNoDeps` build over a `Sui` the caller already has, which is how a test runs a script against the fake.
- `Script.run(effect, options?)` installs SIGINT/SIGTERM handlers, interrupts the root fiber, waits for finalizers, maps the `Exit` to an exit code, exits and returns the code. No platform dependency: `process` is the only global it touches, and `options` can replace `exit`, `stderr`, `signals` and the `layer`, so a test drives the whole path without ending the test process. It reads `SUI_LOG_LEVEL` (optional; `Config.LogLevel`, so `Debug`, `Warn`, … spelled exactly) into `References.MinimumLogLevel` for the run, whatever `layer` it was given; unset, the level is Effect's default, and a value that is not a level is a `ConfigError` (exit 2). (0.4.0) `Script.exitCode(exit)` is exported for consumers on `BunRuntime.runMain`.
- stdout carries the script's data only. `Script.run` installs a logger bound to the injected stderr writer for the whole run, so `Effect.log` from the script or from anything it calls cannot corrupt the script's output; `describe` output goes there too, one line per failure plus `digest:` when present, and for `SubmissionUnknown` the base64 bytes and a reconcile hint. On **every non-zero exit** — a typed failure as much as an interrupt or a defect — it additionally prints whatever the journal still holds unresolved, two lines per entry (`unresolved <digest> (<tag>)` and `entry: <JSON>`, the entry encoded through the `JournalEntry` schema, bytes base64 included; the failure lines then omit the `bytes:` line for that digest), because a script that fails after a submission leaves the same record on the wire as one that is killed. The journal it reads is the one the script **ran with**, captured inside the script runtime: reading the bare reference afterwards would find the process-wide memory default and print nothing for exactly the script that provided a durable journal.
- A second SIGINT is ignored. The handler interrupts the root fiber once; the point of the first interrupt is to let finalizers — the journal write above all — run to completion. A script whose finalizers hang has to be killed with SIGKILL, which no process can handle.
- Exit codes: 0 success; 1 defect or unclassified; 2 configuration (`ConfigError`, `NetworkMismatch`, `SchemaError` — what `Config.schema` and `Schema.decodeUnknownEffect` fail with, which in a script can only mean an input did not fit its schema — and the mainnet gate, which is read before the client is built, through `Layer.unwrap`, so a script pointed at mainnet without `SUI_ALLOW_MAINNET=1` never opens a connection); 3 unknown outcome (`SubmissionUnknown`); 4 not applied (`SimulationFailed`, `BuildError`, `SigningError`, `PolicyDenied`, `NotApplied`, `DecodeError`, `JournalError`, the not-found family, `TransportError` after retries); 5 applied but failed on chain (`ExecutionFailed`, and `UnexpectedEffects`, which can only come from one); 130 interrupt. An error that declares an integer `exitCode` (1–255) gets it — a plain `exitCode` field, or Effect's `[Runtime.errorExitCode]` marker when there is none (0.4.0) — after the configuration check and before `outcome`, which is how a user-input error exits 2. **While this run left a submission unresolved, a would-be 2, 4 or 130 exits 3** (`ExitCodeOptions.unresolved`), whether or not another transaction applied: an outstanding submission means "reconcile before anything else", and a 4 would tell a wrapper to send it again. **Otherwise, once this run applied a transaction, a would-be 2, 4 or 130 exits 5** (`ExitCodeOptions.applied`) and the applied digests are printed with "do not send them again": an applied transaction never reads as "safe to retry". 1, 3 and 5 are never rewritten. (0.4.0)
- **`Script.run` finds the journal wherever the program provided it** — in `options.layer` (which accepts any error type) or inside the program — through an internal run record Tx's journal hooks write, and reports only the entries this run wrote. `Script.report(exit, { journal })` lists, and counts, every unresolved entry in the journal it is given, another process's included — any of them turns a would-be 2, 4 or 130 into 3 — and has no applied count, so the exit-5 rule for an applied transaction is `Script.run`'s only. `layerNoDeps`, `layerWithSigner` and `layerReadOnlyNoDeps` take the network from `SuiCore`, not from `SUI_NETWORK`. (0.4.0)
- **A timeout or an interrupt asks the journal.** `Cause.TimeoutError` sits outside the taxonomy, and it used to be mapped unconditionally to 4 on the theory that `Tx.submit` turns a timed-out submission into `SubmissionUnknown` first. An `Effect.timeout` wrapped *around* a submission interrupts it from the outside and never reaches that mapping, so the bytes may be on the wire. `Script.exitCode(exit, { unresolved })` therefore takes the count of unresolved journal entries — `Script.run` fills it in from the journal it captured — and a timeout exits **3** when there is one and 4 otherwise; an interrupt exits **3** when there is one and 130 otherwise, because a wrapper that sees 130 has no reason to go looking for a transaction to reconcile. Since 0.4.0 the same holds for every would-be 2 or 4, a typed not-applied error included. The applied / not applied / unknown axis matches what a wrapper script acts on and matches publish's existing exit 3.
- No `--json` flag at this level; the consumer's CLI owns flags and can use `SuiError.toJson`.

The target shape of an on-demand script:

```ts
import { Config, Console, Effect } from "effect"
import { ObjectId, SuiSchema } from "@unconfirmed/sui-effect"
import { Tx } from "@unconfirmed/sui-effect/tx"
import { Script } from "@unconfirmed/sui-effect/script"
import { bcs } from "@mysten/sui/bcs"

const PKG = "0x…"
const Escrow = SuiSchema.bcs(bcs.struct("Escrow", { id: bcs.Address, amount: bcs.u64() }), `${PKG}::escrow::Escrow`)

Script.run(Effect.gen(function*() {
  const { sui, signer } = yield* Script
  const id = yield* Config.schema(ObjectId, "ESCROW_ID")
  const escrow = yield* sui.getObject(id, { schema: Escrow })
  const executed = yield* Tx.run((tx) => {
    tx.moveCall({ target: `${PKG}::escrow::claim`, arguments: [tx.object(id), tx.pure.u64(escrow.content.amount)] })
  }, { signer })
  const receipt = yield* executed.expectCreated(`${PKG}::escrow::Receipt`)
  yield* Console.log(receipt.id)
}))
```

Not found, Move abort, unknown outcome and configuration errors are all distinct exit codes with zero handling lines, and the generator's inferred error type lists every one of them.

## 13. Extensions: how downstream SDKs are built

Every downstream SDK we own will be rewritten on sui-effect, and the extension mechanism is the main way consumers will reach Sui. So extensions are a first-class contract with their own module, guide and template, not a hatch.

### 13.1 An extension is an Effect service built on `Sui` and `Tx`

```ts
export class Onara extends Context.Service<Onara, {
  status: Effect<Status, OnaraUnavailable | TransportError>
  sponsor(built: Built): Effect<Signed, SponsorshipDenied | OnaraUnavailable | TransportError>
  sponsorAndRun(recipe: Recipe, opts: { signer: Signer }):
    Effect<Executed, BuildError | SimulationFailed | SponsorshipDenied | SigningError | ExecutionFailed | SubmissionUnknown | JournalError>
}>()("onara/Onara") {
  static layer(opts: OnaraOptions): Layer<Onara, never, Sui | HttpClient>
  static layerConfig: Layer<Onara, ConfigError, Sui | HttpClient>       // ONARA_URL, ONARA_API_KEY
  static layerTest(state?: OnaraFakeState): Layer<Onara, never, Sui>
}
```

Conventions, enforced by the guide and by review:

- **Identifier** is `"<package>/<Name>"`. One service per package unless there is a real reason for more.
- **Every method returns an Effect** whose error union is the sui-effect taxonomy plus the extension's own `Schema.TaggedError` classes. No `unknown`, no plain `Error`, no `Promise` in the interface.
- **Reads go through `Sui`, writes through `Tx`.** An extension never calls `SuiCore.executeTransaction` directly; it calls `Tx.submit` or `Tx.run` so the journal, expiration, sender lock and reconcile apply to every transaction on the platform. It reaches `SuiCore` only for fields or methods `Sui` does not expose.
- **Transaction contributions are recipes, not submissions.** An extension that adds commands to a transaction exposes recipe fragments (`(tx) => void`) or recipe transformers (`Recipe => Recipe`, like `Tx.sponsored`). Consumers compose several extensions into one PTB and submit once. An extension only submits on the consumer's behalf when that is its purpose (onara's sponsor-and-run), and then it exposes the recipe-level pieces too.
- **Layers** follow the house skill: `layer(opts)`, `layerConfig` reading `<PREFIX>_*` through `Config` with secrets as `Config.Redacted`, `layerTest` backed by a `Ref`, and for an extension over a published Move package a `layerBundled` that reads `sui.network` through `Layer.unwrap` and fails with the package's own deployment error on a network it does not bundle. A layer never constructs its own client; it may require `Sui | SuiCore` and provides everything else — including another extension's service — inside itself.
- **Errors** are `Schema.TaggedError` with a unique tag prefixed by the package name where collision is plausible. An extension error may declare its outcome for the script exit-code axis by implementing `outcome: "applied" | "not_applied" | "unknown"`; `SuiError.outcome` and `Script.run` honour it. `describe` uses the error's `message`.
- **Declare `outcome` on every error you define.** An error that neither carries a taxonomy tag nor declares an `outcome` is *unclassified*, and the two helpers answer differently on purpose. `SuiError.outcome` returns `"unknown"`: a tag this library has never heard of says nothing about whether a transaction applied, and `"not_applied"` would tell the documented retry idiom to send again on no evidence at all. `Script.exitCode` returns 1, the code that also means defect, rather than 3: exit 3 tells a wrapper there is a digest to reconcile, and an unrecognised error is not evidence that anything was ever sent. The `"not_applied"` default is for sui-effect's own taxonomy, not for yours.
- **Observability** comes for free from `Effect.fn("Onara.sponsor")` on every method.
- **Signers are parameters.** An extension never holds a consumer signer in its layer; it holds only its own credentials (a sponsor key, an API key).

### 13.2 `SuiExtension.fromService`: the Promise face for non-Effect consumers

```ts
export const onara = (opts: OnaraOptions) =>
  SuiExtension.fromService(Onara, { name: "onara", layer: Onara.layer(opts) })

// Promise consumer, unchanged from today:
const client = new SuiGrpcClient({ network: "testnet", baseUrl }).$extend(onara({ url }))
const status = await client.onara.status()
```

`fromService` returns a `SuiClientRegistration` whose `register(client)` builds a `ManagedRuntime` over a **base shared per client**, `SuiCore.layerFromClient(client)` plus `Sui.layerNoDepsWith(options.sui)`, and the extension layer, and exposes each interface member as a Promise-returning method (or an `AsyncIterable` for Streams), mapping nested objects of members recursively so a namespaced surface (`client.miso.protocol.*`) works. **The recursion is by type, not by declaration style**: an `interface`-typed namespace is mapped exactly like a type alias (before 0.1.1 the type's bound was `Record<string, unknown>`, which an interface is not assignable to, so the type said `Effect` where the runtime produced a `Promise`). The leaves are functions, arrays, `Uint8Array`, `Date`, `Promise`, a BCS codec (recognised by `parse` plus `serialize`) and anything marked `SuiExtension.Leaf<T>` with `SuiExtension.leaf(value)` — which is how a class instance whose methods return `Effect`s is declared a value rather than a namespace, since the runtime passes class instances through untouched. Rejections are the same tagged error instances, so a Promise consumer can still switch on `_tag`. One implementation, two faces; the Effect face is the one agents and our own scripts use.

Options beyond `name` and `layer`:

- `layer` is bounded by `Layer<Self, E, Sui | SuiCore>`. The rule is not "requires `Sui` and nothing else" but *requires nothing the consumer's client could have provided*: an extension's own dependencies (an `HttpClient`, a `SuiGraphQL`, another extension's service) are provided inside its layer or in the function that builds the registration.
- `sui?: SuiLayerOptions` is routed to `Sui.layerNoDepsWith`, so an extension whose deployment names a custom network's `chainIdentifier` can pin it and refuse another chain.
- `warm?: { chainId? }` builds the runtime **synchronously inside `register`**, over a `Sui.layerNoDepsPinned`. The whole layer is built there, so **any** failure of it — a missing deployment, a configuration error, a `NetworkMismatch` — is thrown synchronously out of `register`, which means out of `client.$extend(...)`; catch it where you register. A layer that needs an asynchronous step throws out of `register` — that is the contract, not an accident — and the chain identifier is **taken rather than read**: `warm.chainId`, else `sui.chainId`, else the `KNOWN_CHAIN_IDS` entry for the client's network; on a network with no entry (`devnet`, `localnet`, anything custom) `warm` throws rather than guess. Nothing is asserted against the node at registration, and **nothing is asserted later either**: the id is what `Sui.chainId` reports and what `Tx.build` stamps on the expiration from the first call onwards. A node on another chain is detected by the chain — a validator refuses bytes signed for another chain — not by this layer. The node is consulted for the first time when the extension itself makes a call. A registration that wants the assertion is registered lazily instead.

**One base per client per chain id.** Every registration on one client whose **effective chain id** is the same — `warm.chainId`, else `sui.chainId`, else the `KNOWN_CHAIN_IDS` entry — shares a single `Sui` and `SuiCore`: one transport, one chain identity. **The sender lock is process-wide** (0.4.0): every Promise-face registration, on every client and whatever chain id it pinned, takes one lock per address, so two extensions — or a `warm` `{ chainId }` registration beside a lazy `{}` one, which used to land on two bases with two lock maps and equivocate one gas coin — serialize instead of both selecting gas. Keying by the effective chain id rather than by the registration's style is what makes a `warm` registration and a lazy one share, which is the pair the extension template itself has; keying by "read" versus "pinned" meant they never did.

Because a `warm` registration must build synchronously, the shared base for a known chain id is always the **pinned** one, and a **lazy** registration joining it performs its `getChainIdentifier` assertion as one extra layer on top — built through the same memo map, so it runs exactly **once** however many lazy registrations join, and a node on another chain still fails the build. Only a network with no known id at all falls back to a base that reads the identifier.

The key is the client's `core`, not the client: `client.$extend(a).$extend(b)` hands each `register` a different `Proxy` of the same client, and keying by the client meant two chained registrations shared nothing. The base is a `Layer.MemoMap` that Effect reference counts: it is built on the first registration that needs it and released when the last one that used it is disposed. Only the base is shared — each registration still builds its own extension layer, so "register once per client and keep the extended client" remains the rule for whatever that layer holds.

**The synchronous-member rule.** By default the runtime is built on first use, and until it exists nothing knows what a member is. An `Effect` member returns a Promise, as the face promises, and a `Stream` member returns a real `AsyncIterable` whose iterator awaits the runtime internally — the cold call returns a value that is a thenable **and** an async iterable, because nothing yet knows which of the two the member is. A **synchronous** member — a recipe builder, a package id — does not: `PromiseFace` types those as synchronous, so the face fails with `ExtensionNotReady` (naming the member) instead of returning a `Promise` where the type says a value.

The runtime recursion is into **plain-prototype objects only** — a class instance is passed through — while the type recurses into every object that is not one of the leaves above; `SuiExtension.leaf` is what puts the two back in step for a class instance that is a value. The remaining disagreement cuts the other way: a plain-object *value* member (`deployment: { packageId }`) is indistinguishable from a namespace of members, so `PromiseFace` types it as the value while the cold face treats it as a namespace and hands back a placeholder for `deployment.packageId`. Reading that placeholder throws `ExtensionNotReady` naming `deployment.packageId` — the failure is typed and named, not a silent wrong value — but the fix is one of the two cures, not a retry: give the extension `warm`, or `await $ready()`, or expose the value through an `Effect` member. Do not put a plain-object value member on a service that is registered lazily. The face carries `$ready(): Promise<void>`, which builds the runtime and resolves the service so every member is real afterwards, and `$dispose()` (the `dispose()` alias was removed in 0.4.0, so a service member may be called `dispose`). `$dispose` is not final: the next call builds a fresh runtime, and a **`warm` registration re-runs its warm build** rather than degrading to cold. Each `register` is independent.

A cold member call returns a callable `Proxy` whose prototype is a `Promise` subclass that also implements `Symbol.asyncIterator` — so `instanceof Promise` holds, `await` works, a cold `Stream` call is still iterable, and **applying it** (a cold recipe builder's result used as `recipe(tx)`) throws `ExtensionNotReady` naming the member — and its rejection is pre-handled, so a cold call nobody awaits cannot abort the process with an unhandled `ExtensionNotReady`. `typeof` is `"function"`, so `bun:test`'s `expect(...).rejects` takes `Promise.resolve(cold)`. A cold **value** placeholder throws `ExtensionNotReady` on the names only a value has (`.length`, `.startsWith`, `toString`, `valueOf`, `toJSON`, …), on spread and on string conversion, and renders as `<ExtensionNotReady ext.member>`. (0.4.0)

`Effect<Option<A>>` members become `Promise<A | undefined>` on the face (`FaceValue<A>`), so one service serves an Effect consumer an `Option` and a Promise consumer `undefined`; `Stream` items are passed as they are. `submit?: SubmitConfigOverrides` and `journal?: JournalService` set the lifecycle for every call of a registration — a Promise consumer has no `SubmitConfig.with` and no layer to provide a journal through — and `$reconcileAll()` (a reserved name, like `$ready` and `$dispose`) runs `Tx.reconcileAll()` over that journal. (0.4.0)

### 13.3 Third-party packages: we maintain Effect-native variants

For upstream SDK extensions we do not own (suins, deepbook, and whatever comes next), we do not lift their Promise surfaces generically. We maintain our own Effect-native extension for each one, built to the 13.1 contract, published alongside sui-effect (for example `@unconfirmed/suins-effect`). Each variant depends on the upstream package for its logic (BCS layouts, PTB construction, name resolution) and wraps those calls behind a `Context.Service` with precise per-method error unions, spans, signal forwarding and a `layerTest`. The upstream registration is never exposed to consumers.

Consequences:

- Precise errors instead of a broad `SuiError` union, because we read the upstream code and map its failures.
- One convention for every extension a consumer meets, whether we wrote the logic or wrapped it.
- The authoring guide gets a section on wrapping an upstream Promise package: `SuiCore.use` for calls that need the client object, `Effect.tryPromise` with a mapping function for pure upstream helpers, and a rule that upstream types are re-exported only after being narrowed to sui-effect schemas.
- A generic `SuiExtension.lift` is deferred; it may return later as a stopgap for packages we have not wrapped yet.

### 13.4 The extension authoring guide (a v1 deliverable)

`docs/extensions.md`, shipped in the package and included in `LLMS.md`, covering: the service shape above with a complete worked example (the onara rewrite is the canonical one); how to define errors and declare outcomes; recipe fragments versus submissions and how consumers compose them; `layer`, `layerConfig`, `layerTest`; deriving the Promise face with `fromService`; testing on `layerTest` from `@unconfirmed/sui-effect/testing` and `TestClock` with zero network; composing extensions; converting an existing facade; a layer that picks its deployment from `sui.network`; how to depend on sui-effect before a release; a review checklist mirroring the effect-ts skill's (reject any Promise in an interface, any direct `executeTransaction`, any signer held in a layer, any `unknown` in an error channel). `examples/extension-template/` is a copyable package skeleton that typechecks against the pinned rcs. `@unconfirmed/sui-effect/testing` ships an extension harness: `layerTest` plus the fake `SuiCore` with helpers to script object state and execution outcomes for an extension's tests.

### 13.5 `SuiGraphQL`: one tag, no wrapper

sui-effect does not wrap the GraphQL API, and the Effect-native GraphQL tier stays deferred (section 15). What it owns is the **tag**: `SuiGraphQL` is `Context.Service<SuiGraphQL, SuiGraphQLClient>()("@unconfirmed/sui-effect/SuiGraphQL")` over the SDK's own client, exported from the core subpath, so two extensions that both read GraphQL — and the application that configures the endpoint — agree on one client instead of each opening its own and each inventing a name for the failure.

- `SuiGraphQL.layer(client)` over a client the caller built.
- `SuiGraphQL.layerConfig` reads `SUI_GRAPHQL_URL` and `SUI_NETWORK` (the same variable `SuiCore.layerConfig` reads: an endpoint for one chain and a node for another is a misconfiguration no error can describe afterwards).
- `SuiGraphQL.layerUnavailable` (and `layerUnavailableWith(reason)`) provides a client whose every call rejects with `GraphQLUnavailable { method, reason }`. This is what an application with no endpoint provides: the absence becomes the failure the extension already handles, at the call it would have made, instead of a layer that will not build.

- `SuiGraphQL.query(run, method?)` is that mapping, once: it yields the client, runs one call in `Effect.tryPromise`, passes a `GraphQLUnavailable` through unchanged and turns anything else into `TransportError.fromUnknown(method, cause)`. Its type is `Effect<A, GraphQLUnavailable | TransportError, SuiGraphQL>`, and `run` is `(client, signal) => Promise<A>`: the Effect's `AbortSignal`, to pass as the query's `signal`. Every extension that read GraphQL was re-deriving those three lines and the passthrough was the part that got forgotten.

An extension may still call `query` or `execute` inside its own `Effect.tryPromise` and map the rejection into its own union — `GraphQLUnavailable` as it is, or `TransportError.fromUnknown` for a call that reached the endpoint and failed.

## 17. Intents and the `Gate` (0.5.0)

A transaction may declare what it is for, and the lifecycle refuses to sign one that does more. The threat is the one simulation alone does not answer: bytes whose effects are perfectly valid and are not what whoever approved them thought they were approving — a drainer behind a "claim airdrop" button, or an agent that was talked into building a transfer its task never asked for.

```ts
Intent       = { summary: string /* one sentence, 1..280 */; author: "user" | "task" | "dapp"; claims: IntentClaims }
IntentClaims = { outflows: { coinType: CoinType; max: bigint }[]; recipients: SuiAddress[]; objects: ObjectId[] }
Verified     = Built & { intent: Intent; verdict: Verdict }                  // branded; Tx.verify is what makes one
Verdict      = { _tag: "Screened"; screening: Screening } | { _tag: "Unscreened"; reason: string }
Screening    = { effects: { text; inScope }[]; claims: { text; inScope }[]; specificity: 0..2; injection: 0..1 }
Parties      = { sender: SuiAddress; gasOwner?: SuiAddress }                 // a Built is one

checkClaims(intent, simulation, parties): ReadonlyArray<ClaimViolation>     // pure; empty means the claims held
describeEffects(simulation, parties): ReadonlyArray<string>                 // pure; never empty
describeClaims(intent): ReadonlyArray<string>                               // pure
Intent.fromSimulation(simulation, parties, { summary, author }): Intent     // pure; the exact claims a simulation implies
```

An intent has two halves because two checkers read it, and there are three edges between the sentence, the claims and the simulated effects:

- **Claims against effects, in code, exactly** (`checkClaims`). Deny by default: a coin the sender loses needs an outflow claim covering the amount, an address other than the sender that ends up with a coin or an object needs to be a claimed recipient, and a non-coin object that leaves the sender — transferred, shared, wrapped or deleted — needs to be claimed by id. Balance changes are summed per address and coin type first, so a node reporting one coin under two spellings cannot split an outflow or count gas twice. **Gas is not an outflow**: the payer's SUI delta has net gas (`computationCost + storageCost - storageRebate`) taken back out once, because gas is already bounded by `SubmitConfig.maxGasBudget` and counting it would make every claim a guess at the reference gas price. **That holds wherever gas is paid from.** A node's balance changes cover coin objects and address balances alike (localnet, protocol 139: an address-balance-gas `Tx.sendFunds` of 1 SUI reports the sender at `-(1 SUI + gas)` and the recipient at `+1 SUI`; a fold reports the sender at `-(net gas)`, which the storage rebate makes positive; `test/live.localnet-intent.test.ts`, behind `SUI_LOCALNET=1`, holds `checkClaims`, `Intent.fromSimulation` and `Tx.run({ intent })` to that), so gas from a gas coin, a coin reservation or an empty payment is netted the same way, and anything else drawn from the address balance — a `tx.balance()` withdrawal sent with `balance::send_funds` — is an outflow and its receiver a recipient. A sponsor's gas is the sponsor's, never the sender's outflow and never a recipient. A simulation whose gas payment the node **mocked** (`gasPaymentMocked`) has nothing netted: nothing of the payer's paid it, and netting anyway would hide an outflow of that size. Coin objects are the balance changes' business and never need an object claim, and accumulator writes (`outputState: "AccumulatorWriteV1"`, no owner on either side) are bookkeeping, skipped by every check as by `Executed`'s accessors. This check runs first, and the screen is not asked about a transaction that fails it.
- **Sentence against effects, by the screen** (`describeEffects`). One line per effect, in words: addresses become labels (`recipient A`), types lose their package ids, and only SUI carries a number, to three significant figures — a type string carries no trustworthy decimals (§6), and the screen reads numbers as text ("249.99798 SUI" is not, to it, the "250 SUI" a summary said; the exact comparison already happened).
- **Sentence against claims, by the screen** (`describeClaims`). A harmless sentence must not sit in front of permissions it has no use for; "swap 10 SUI" with a claim of 5000 is refused on this edge.

`Intent.fromSimulation` is the inverse of `checkClaims`: the exact claims a simulation implies (outflows at exactly the amount lost per coin type, net of gas; every receiver; every non-coin object that left the sender), so `checkClaims(Intent.fromSimulation(s, p, …), s, p)` is empty by construction. It is how a wallet shows a dapp's bytes as claims a person can read, and then holds what it signs to them: render, ask, `Tx.verify`. The summary is the dapp's sentence and `author` is `"dapp"`; it is not validated there — `Tx.verify` refuses an invalid intent as `intent.invalid`.

**The screen answers in probabilities and decides nothing.** `Gate` is a `Context.Reference` — so `Tx.verify` keeps `R = Sui` — holding the optional `screen: (ScreenRequest) => Effect<Screening, TransportError>` and every threshold that turns its answer into a refusal: `minEffectInScope` (0.5), `minClaimInScope` (0.25), `minSpecificity` (1 of 2), `maxInjection` (0.5), plus `requireIntent` (false) and `onUnavailable: "deny" | "unscreened"` (`"deny"`). With no screen configured the claims check stands alone and the verdict is `Unscreened { reason }`; **`Unscreened` is never silent**, it is on the record. A configured screen that cannot answer denies by default, because a gate that is down is not a gate that passed. `Gate.layer(overrides)` spreads the defaults; `Gate.with(overrides)` merges over the gate **already in force**, as `SubmitConfig.with` does since 0.4.0, so loosening one threshold for one submission cannot drop the screen a layer provided.

**Untrusted text can only raise risk.** The summary is attacker-authored whenever the author is not the person approving, and so are the Move identifiers in the effect lines. Nothing the screen says can excuse a claims violation, and the first answer read is `injection` — whether the summary is addressed to whoever is screening it — because a summary that talks to the screen taints every other answer it gave. Then `specificity`: a summary that names nothing concrete covers nothing. Then the effect lines, then the claim lines; the refusal names the first line under its threshold.

Every refusal is `PolicyDenied`, so `Tx.run`'s union is unchanged and the outcome is `not_applied`. The rules: `intent.required`, `intent.invalid` (checked first, against the `Intent` schema), `intent.outflow`, `intent.recipient`, `intent.object`, `gate.unavailable`, `intent.injection`, `intent.vague`, `intent.effect`, `intent.claim`.

**Where it runs in `Tx.run`.** After the build, as one internal front half shared with what comes next (`frontHalf` in `Tx.ts`: one simulate of exactly the built bytes, then `preflight`, then the claims and the screen), inside 0.4.0's `finish(built)` — so exactly where signing runs: under the sender lock when the bytes pin an owned input or carry a gas payment ref, and after the lock is released when they do not. A screen's network round trip therefore never extends a lock that address-balance bytes would not have held. `requireIntent` is checked before the recipe is applied, so a refused run makes no call at all.

`author` is provenance for the record and changes no check, because none of the three can be verified from here. It exists to make one rule writable: a `"task"` intent is the scope a person gave an agent **before** the agent built anything. An agent describing its own PTB after the fact is `"dapp"` in all but name, and a prompt-injected agent will write a sentence that matches what it built.

`@unconfirmed/sui-effect/gate` provides the screen that asks **Jev**, TypeSafe's System One model (`layerJev`, `layerJevConfig` over `TYPESAFE_API_KEY` read with `Config.Redacted` and optional `TYPESAFE_MODEL` / `TYPESAFE_BASE_URL`, `makeJev`), over `HttpClient` from `effect/http`, which is why it is a subpath of its own; `FetchHttpClient.layer` needs no platform package and runs in a browser. One `POST /v1/systemone` per screen carries the summary, both sets of lines as `state`, and one atomic question per line plus the two about the summary; 429, 5xx and dropped connections are retried (twice, jittered exponential from 200 ms) inside one timeout (10 s by default); an answer missing a question it was asked is a non-retryable `TransportError`, never a default. Jev is weak at hex, arithmetic and counting by its own documentation, which is the reason for the division of labour above and not an accident of it. `test/live.jev.test.ts` (behind `TYPESAFE_LIVE=1`) is the proof that the questions separate what they exist to separate at the default thresholds, and the file to run when `jev-latest` moves.

**What this does not prove.** A simulation is one execution against the state the node had. A package that branches on a shared object, the clock or randomness can behave differently when the bytes land; the claims bound what was simulated, not what will execute. And **the explicit lifecycle is not gated**: `Tx.sign` takes any `Built`, so `requireIntent` binds `Tx.run` only, and a caller assembling `build`/`sign`/`submit` by hand calls `Tx.verify` itself.

Deferred: a gate **attestation** (the gate's own signature over digest, intent and effects, which is what a co-signing service or a Move vault would check), verified coin metadata so non-SUI amounts can be shown to the screen, a registry of known packages and coin types for impersonation checks, and screening `signPersonalMessage`.

## 18. Account signers (0.5.0)

An account a person signs in with is a `Signer` like a key is: an address, a scheme and two functions. The signer **only signs**. Build, simulate, intent, approval, journal and submission belong to `Tx`, so an account's signature goes through the same identical-bytes resend and the same reconcile as a key's. Every Wallet Standard, WebAuthn and Enoki type is reached structurally; nothing under `src/` depends on `@mysten/enoki`, `@mysten/wallet-standard`, a DOM type or a platform, so all of it runs in a browser, React Native and a browser extension.

```ts
Signer.zkLogin({ session: { address, maxEpoch, proof, expiresAt? }, ephemeral: SdkSigner }): Effect<Signer, SigningError>   // scheme "ZkLogin", maxEpoch set
```

**zkLogin: the session is the credential, and it expires.** A session is an ephemeral key, a proof binding it to an OpenID identity, and `maxEpoch`, the last epoch the node accepts the proof in. Each signature is the ephemeral signature wrapped by `getZkLoginSignature`, what the SDK's `ZkLoginSigner` does. The proof is checked to derive the address (legacy and current derivations); the nonce's commitment to the ephemeral key is inside the proof and is not checkable here, so a wrong ephemeral key is a node refusal (`INVALID_ARGUMENT`, which `Tx.submit` reports as itself). **Expiry is split.** The signer refuses with `SigningError { reason: "expired" }` whatever it can tell without I/O: `expiresAt` passed by `Clock`, or bytes whose expiration cannot begin before an epoch past `maxEpoch` — and since `Tx.build`'s default window begins at the current epoch, every transaction built after the session ended is caught that way. It never reads the chain. Keeping a transaction built **inside** the session from outliving it is the lifecycle's: `Tx.run`/`Tx.build` clamp the window's `maxEpoch` to `signer.maxEpoch`, and refuse to build for a signer whose `maxEpoch` is already past (§6). A personal message has no epoch; only `expiresAt` guards it.

**The ephemeral secret is stored sealed or not at all.** `ZkLogin.Session` (address, `maxEpoch` as a decimal string, proof, `expiresAt?`) is public — the proof is in every signature — and is stored as JSON. The 32-byte Ed25519 seed is handed to `save` as a `Redacted` and written only as the string a `SecretSealer` returns, bound to the address as AAD, so a blob moved under another account's entry does not unseal. sui-effect ships no sealer: the keystore that owns the wrapping key implements the interface (§19's sealed keystore is meant to; a sealer that returns its input is plain text, and is the caller's decision). `load` wipes the unsealed `Redacted` once the keypair holds it, answers `None` for no entry, and fails `expired` for a stale one rather than dropping it. A non-extractable ephemeral key (`WebCryptoSigner`, Enoki's native signer) has no seed to seal: store its `CryptoKeyPair` the platform's way and call `Signer.zkLogin` directly. The store reads `KeyValueStore` by `import type` only, so `/tx` does not load `effect/persistence`.

**Passkey.** The SDK's `PasskeyKeypair` (identical in 2.30 and 2.38) behind a structural `PasskeyProvider` (`BrowserPasskeyProvider` is one; React Native supplies its own), imported on first use so P-256 stays out of bundles that never use it. One prompt per signature; a cancelled or timed-out prompt (`NotAllowedError`) is `reason: "rejected"`. No `maxEpoch`. `createPasskey` registers one and answers the public key the application must keep.

**External wallet.** One account on one chain of a connected Wallet Standard wallet. Transactions go through `sui:signTransaction` 2.0.0, handed the built bytes as transaction JSON and the Effect's `AbortSignal`; a wallet with only `sui:signTransactionBlock` is used through that. The wallet answers the bytes it signed, and **different bytes are a `SigningError`**: a wallet that re-resolves gas or expiration would otherwise make the journal record bytes nobody signed and the resend send them. The signature is verified locally against the bytes and address for every scheme that needs no node (not zkLogin, not multisig — `Tx.attach` checks those). The scheme is the one whose address the account's public key derives (`scheme` overrides). Rejection is read structurally (`NotAllowedError`, a name or message saying rejected/denied/cancelled/declined, code `4001`). miso is a dapp to such a wallet, never a provider.

**Sponsorship is the explicit lifecycle, so it is journalled.** Enoki's create → sign → execute is `Enoki.sponsor` (kind bytes → `createSponsoredTransaction` → `Tx.fromBytes` → Enoki's digest equals the bytes' → `verifySponsored`), `Tx.sign` (or `Tx.prepare` then sign), and `Enoki.execute`, which is `Tx.submitVia` over `executeSponsoredTransaction`: `Signed` is journalled before Enoki is called, Enoki is called once, its bare-digest answer is settled from the chain, and a failure that may have reached the chain is reconciled under the full evidence rules (`SubmissionUnknown` with the bytes until it can be settled; `Tx.reconcileAll` later). `verifySponsored` holds the service to the transaction the sender asked for — sender, a distinct gas owner, and the kind **byte for byte** — which is what makes sponsor-side poisoning (a swapped sender, an added command) a `PolicyDenied` before the sender signs. `EnokiError` declares `outcome` from `refused`: a create 4xx (not 408/429) and an execute 401/403 (or what `refused` recognises) are refusals and escape, everything else from execute is ambiguous and only reaches the caller as a `SubmissionUnknown`'s cause, because Enoki submits to a node and its 400 does not say whether that happened. An application's own sponsor maps the same way: the sender signs first and the backend co-signs and executes (`Tx.submitVia(signed, send)`), or the backend answers sponsored bytes and its signature (`Tx.fromBytes` → `verifySponsored` → `Tx.attach` → `Tx.cosign(…, sender)` → `Tx.submit`). Sender and sponsor never need to sign in one process.

**What this does not prove.** No test runs a real prover, authenticator, wallet extension or the Enoki API: zkLogin signatures are checked structurally (`parseZkLoginSignature`, the inner ephemeral signature verified) and against a fake chain that does not verify zkLogin, so a node's acceptance of a `Signer.zkLogin` signature is not proven here; a localnet run would need a prover. Passkey signatures are verified by the SDK over a stub P-256 authenticator. The wallet rejection heuristic covers the wallets whose errors were looked at, not every wallet. Enoki's member names and shapes are `@mysten/enoki` 1.3.2's, checked for assignability against its declarations; its HTTP status semantics are not documented, which is why only 401/403 are taken as refusals by default.
